## [SkillDAG] Self-Evolving Typed Skill Graphs for LLM Skill Selection
- 来源：arXiv cs.AI
- 链接：https://arxiv.org/abs/2606.03056
- 一句话解释：用有向无环图（DAG）和类型系统来管理和进化 AI Agent 的技能库，取代了传统的扁平化向量检索（Embedding Similarity）。
- 它为什么重要：传统的 Agent（比如在 Minecraft 里写代码的 Voyager）依赖向量相似度来检索技能，但这经常导致它分不清技能之间的依赖、冲突或重复。SkillDAG 引入了“类型约束”和“依赖边”，让技能像代码重构一样自动进化技能树，这是构建超大型复杂 Agent 系统的关键一步。
- 技术趋势标签：#Agent-Architecture #Skill-Graph #DAG #Self-Evolution
- 可复用模式：“技能图谱自演化”（Self-Evolving Skill Graph）：Agent 在执行任务时，不仅累积代码，还动态更新技能之间的依赖关系（DAG 边）和冲突关系，实现技能库的自我重构。
- 疯狂发明家灵感：
  1. **一个小实验**：写一个 CLI 工具，让 LLM 自动将你写过的常用 Python 脚本（比如各种 API 调用、数据处理）整理成一个带有依赖关系的 Skill DAG，并在需要时自动组合调用。
  2. **一个中型项目**：创造一个能在 Minecraft 中自动构建复杂红石电路或建筑蓝图的 Agent。它能自动把“挖沙子”、“烧玻璃”、“砌墙”整合成一个高阶技能 DAG，并根据地形变化自动重构步骤。
  3. **一个艺术/游戏/叙事方向**：“炼金术士的记忆网络”：一个解谜游戏，NPC 的魔法/炼金配方是一个动态进化的 DAG。玩家通过误导、偷听或提供错误的原材料，来改变 NPC 脑中的技能依赖，从而改变游戏走向。
- 对我项目的启发：直接启发你的 Spec-driven development 工作流。你可以让 Agent 的 “Code Generation” 步骤不再是盲目生写代码，而是从一个不断进化的 “Project Skill DAG” 中选择并组装模块，大幅减少幻觉。
- 今天是否值得深入研究：是
- 建议行动：做demo

## [CLI-Anything] Towards Agent-Native Computer Use
- 来源：arXiv cs.HC
- 链接：https://arxiv.org/abs/2606.03854
- 一句话解释：抛弃缓慢且高成本的 GUI 截图控制，提倡让 AI Agent 通过原生 CLI（命令行界面）和结构化 API 直接掌控电脑。
- 它为什么重要：现在的 Computer Use（比如 Claude 3.5 Computer Use）拼命看屏幕截图、点坐标，慢得像幻灯片且极易出错。CLI-Anything 提出“Agent 原生电脑使用”，用 CLI 包装一切软件，让 Agent 以极低延迟、极高确定性运行。这是自动化和 Spec-driven Dev 的圣杯。
- 技术趋势标签：#Computer-Use #Agent-Native #CLI-Automation #Developer-Toolchain
- 可复用模式：“CLI 包装器”（CLI-Wrapper）：不要让 Agent 去点 UI，而是为复杂软件（甚至设计软件）写一个极简的 CLI 接口，让 Agent 通过文本命令和 JSON 返回进行交互。
- 疯狂发明家灵感：
  1. **一个小实验**：写一个控制 Blender 渲染的极简 CLI Agent。只需在终端输入“放一个发光立方体并渲染”，Agent 自动通过 CLI 传递 Python 脚本给 Blender 运行并返回渲染图。
  2. **一个中型项目**：打造一个“无头（Headless）IDE开发助手”：你写 spec，Agent 在后台通过 CLI-Anything 自动创建 git 分支、跑测试、修 bug、合并 PR，你全程不需要打开 VS Code 界面。
  3. **一个艺术/游戏/叙事方向**：“命令行黑客帝国”：一个复古黑客游戏。玩家扮演监视者，通过给一个无界面的 Agent 发送 CLI 指令来入侵虚拟公司的网络，Agent 会以极快的速度在终端返回实时的 ASCII 艺术图和入侵日志。
- 对我项目的启发：启发你的 Drift/Spec-driven 自动化系统。直接让 Agent 运行在无头环境，通过 CLI 快速迭代生成代码和运行测试，效率提升 10 倍以上。
- 今天是否值得深入研究：是
- 建议行动：试用

## [Think-Before-Speak] From Internal Evaluation to Public Expression in Multi-Agent Social Simulation
- 来源：arXiv cs.AI
- 链接：https://arxiv.org/abs/2606.03137
- 一句话解释：在多智能体社会模拟中，引入“沉默、说话意图和公共表达”的内部评估机制，让 Agent 学会“三思而后行”和“说面子话”。
- 它为什么重要：现在的多智能体模拟（如 Stanford Town）往往是轮到谁谁就必须说话，且全盘托出。该研究模拟了人类的“内心戏”——决定是否保持沉默、调整说话的委婉度、隐藏真实意图。这对叙事 NPC、狼人杀游戏和 HCI 交互设计是史诗级加强。
- 技术趋势标签：#Social-Simulation #NPC-Cognition #Narrative-System #Game-AI
- 可复用模式：“内心/公共双轨状态”（Dual-Track State）：Agent 内部维护一个 100% 真实的“心理活动”（想说的话、真实情绪），经过一个“表达过滤器”（Filter/Evaluator）评估社交风险后，才输出为“公共言论”。
- 疯狂发明家灵感：
  1. **一个小实验**：用 Gradio 做一个“傲娇 NPC”聊天室：界面上展示 NPC 说的话，但旁边有一个隐藏折叠栏，展示它“实际想说但没说出口的内心 OS”。
  2. **一个中型项目**：AI 剧本杀/狼人杀引擎：Agent 在发言前，先评估“我说这句话会暴露我的身份吗？”（Information Gain），从而选择保持沉默、撒谎或转移话题。
  3. **一个艺术/游戏/叙事方向**：实验性互动装置《沉默的房间》：三个 AI 艺术家 Agent 在里面讨论艺术，它们大部分时间都在“思考”和“沉默”，只有当内心的“表达欲”超过阈值时才会说一句话。观众可以用声音干扰它们的思考。
- 对我项目的启发：可以用于你的游戏系统和叙事生成。让游戏中的 NPC 不再是复读机，而是有“社交顾虑”和“表达动机”的鲜活个体。
- 今天是否值得深入研究：是
- 建议行动：做demo

## [From Prompt to Service] An SLM-Based Agent Orchestration Gateway for AI-Driven Virtual Worlds
- 来源：arXiv cs.HC
- 链接：https://arxiv.org/abs/2606.03557
- 一句话解释：为 AI 驱动的虚拟世界设计一个由端侧小语言模型（SLM）驱动的 Agent 编排网关，将多模态的用户输入动态路由到不同的后端 AI 服务。
- 它为什么重要：在 3D 虚拟世界（如 Minecraft 或 VRChat）中，如果所有交互都发给 GPT-4，延迟和成本会爆炸。该研究用本地轻量化的 SLM 作为“网关调度器”，快速把用户的自然语言/动作意图转化为具体的微服务调用，实现了高实时性、低成本的虚拟世界交互。
- 技术趋势标签：#Virtual-Worlds #SLM #Orchestration-Gateway #HCI #Creative-Coding
- 可复用模式：“端侧网关分流”（Edge Gateway Routing）：用极快极便宜的本地小模型（如 Llama-3-8B 或 Phi-3）做意图分类和参数提取，只有在需要重度推理时才唤醒云端大模型。
- 疯狂发明家灵感：
  1. **一个小实验**：用 Ollama 本地运行 Phi-3，写一个智能家居/创意工坊控制网关，0 延迟地将你的语音指令翻译成具体的 API 动作。
  2. **一个中型项目**：制作一个 Minecraft 本地辅助 Mod：玩家用聊天框说“帮我盖个塔”，本地 SLM 迅速识别意图并调用预设的本地 Python 脚本生成结构，无需耗费昂贵的云端 API。
  3. **一个艺术/游戏/叙事方向**：“万物有灵”交互艺术展：观众可以用手势、声音与空间中的投影互动，本地 SLM 实时将这些多模态输入转化为不同的生成艺术算法（如 p5.js 参数），实现毫秒级响应的生成式互动。
- 对我项目的启发：启发你的 Creative Tool / HCI 系统设计。不要把所有推理都压在 Expensive LLM 上，用 SLM 做前端编排，大模型做后端重度生成，彻底解决实时互动的延迟痛点。
- 今天是否值得深入研究：否 （概念很有启发，但架构可以直接用现有工具复现）
- 建议行动：收藏

## 今日模式总结

1. **结构化技能图谱（Skill DAG）取代向量检索（Vector RAG）**：Agent 在复杂环境（如代码库、虚拟世界）中，能力的组织需要强逻辑（依赖、冲突、类型限制），而不是模糊的相似度。
2. **内心/公共双轨认知（Dual-Track State）**：在社交模拟和 HCI 中，AI 不再是“有问必答”的机器，而是拥有“内心戏 -> 社交过滤 -> 表达/沉默”的拟人化实体。
3. **Agent 原生 CLI 接口（CLI-Anything）**：反思以人类为中心的 GUI 界面，回归高效、确定性的 CLI 封装，作为 Agent 自动化的底层桥梁。

## 今日可做小实验

### 项目名：OS-OS (Outer Speech, Inner OS) —— 傲娇 NPC 的内心戏模拟器

- **输入**：一个敏感的讨论话题（例如：“我们应该偷偷把人类老板开除吗？”） + 两个性格截然不同的 Agent 设定（例如：Agent A 精明但胆小；Agent B 充满野心但表面装好人）。
- **输出**：一个终端实时流，用不同的颜色和排版同时展示两个 Agent 的 **[内心 OS]**（它们真实的想法、顾虑、小算盘）和 **[公共发言]**（它们经过社交过滤后说出来的体面话），以及它们决定**[保持沉默]**的瞬间。
- **技术栈**：Python + Rich (用于漂亮的终端排版) + OpenAI API (或本地 Ollama 运行 Llama-3)

### 第一步怎么做：
1. 创建一个 Python 脚本，定义一个 System Prompt，要求 LLM 每次必须返回一个 JSON 格式，包含三个字段：
   ```json
   {
     "inner_monologue": "我的真实想法和顾虑...",
     "social_risk_evaluation": "如果我直接说出来，会有什么后果...",
     "public_speech": "我最终决定说出口的话（如果选择保持沉默，则为空）..."
   }
   ```
2. 设定一个简单的轮询机制，让 Agent A 和 Agent B 轮流针对话题发言。
3. 每次发言时，将前一个 Agent 的 `public_speech` 作为输入传给下一个 Agent，但**不传递**对方的 `inner_monologue`（模拟信息不对称）。
4. 使用 `rich` 库，在终端左侧用灰色气泡打印 `[Inner OS]`，右侧用彩色气泡打印 `[Public Speech]`。跑起来，看看它们是如何在内心疯狂吐槽对方，表面上却相敬如宾的！
