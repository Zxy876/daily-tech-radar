# 疯狂发明家技术雷达 - 2026-10-23

为你筛选出今日最值得关注的 4 个项目。今天 arXiv 展现出一个极其明确的技术暗线：**Agent 正在从“纯文本/扁平检索”转向“结构化程序记忆与可观察经验的动态沉淀”**，这对 Spec-driven 开发、游戏 NPC 长期演进以及复杂自动化工具链有直接的系统级启发。

## 1. SPEM: 面向高效技能调用的结构感知程序记忆
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2610.26995
- **一句话解释**：告别向量检索的“扁平文档堆”，它把 Agent 的技能库变成了一张包含依赖关系、执行顺序、状态转移和数据流约束的“有向图”。
- **它为什么重要**：目前绝大多数 Agent（包括很多 Minecraft 智能体如 Voyager）在技能变多后都会面临检索混乱。SPEM 证明了将技能组织为程序图谱（Procedural Graph）能大幅降低上下文消耗，且保证依赖动作不脱节。
- **技术趋势标签**：#AgentArchitecture #ProceduralMemory #GraphWorkflow #SpecDriven
- **可复用模式**：**结构化技能图谱（DAG-based Skill Registry）** —— 每个技能不仅仅是 `description` + `code`，还显式声明 `pre-condition`、`post-condition` 与 `data-pipe`。
- **疯狂发明家灵感**：
  1. **一个小实验**：为你手头的 CLI 工具写一个简化的 JSON-DAG 技能定义器，让 Claude 不去猜该调哪个，而是沿着前置条件拓扑排序输出工具流。
  2. **一个中型项目**：构建一个 Minecraft 建筑 Agent 的“配方引擎”，Agent 不再瞎搜“造门”，而是沿着“伐木 -> 合成木板 -> 合成门”的程序记忆图谱自动化构建复杂奇观。
  3. **一个艺术/游戏/叙事方向**：生成式戏剧工作流：NPC 的演出技能（“愤怒摔杯”、“下毒”、“拔剑”）依赖于场景的状态前置条件，NPC 在关系网和物理状态变化时自动触发连锁技能图。
- **对我项目的启发**：对你的 Spec-driven workflow 极具启发：Spec 不应该只是静态 Markdown，它可以编译为一张运行时依赖图，Agent 按照状态拓扑自动填补代码实现。
- **今天是否值得深入研究**：是
- **建议行动**：做demo

## 2. REM: 编码智能体经验记忆的存、查、忘机制
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2610.27377
- **一句话解释**：不是单纯记录 Agent 做了什么，而是在代码运行过程中动态观察“哪里试错了、为什么错”，并选择性遗忘冗余步骤，提炼出可泛化的 Debug 经验。
- **它为什么重要**：我们常用的 Copilot / Cursor 每次对话重开后都像“脑震荡患者”。REM 探索了 Agent 在完成长周期软件工程时的元认知（Meta-memory）：明确规定“什么时候该存”、“什么时候该查”、“什么时候必须主动遗忘无用探索”。
- **技术趋势标签**：#CodingAgents #MemorySystems #SelfReflection #DeveloperTools
- **可复用模式**：**经验剪枝与压缩（Trace Pruning）** —— 将数百步包含回退、报错的死循环 Trace，提炼成“触发条件 -> 踩坑记录 -> 正确动作”的三元组，并丢弃冗余细节。
- **疯狂发明家灵感**：
  1. **一个小实验**：给你的终端写一个 Hook，捕获上一条报错命令和修复该报错的命令，调用小型本地模型总结成一条本地 `.drift/learned_rules.md`，每次写代码时注入。
  2. **一个中型项目**：本地自动化“错误抗体系统”——在项目根目录下维护一个 `.agent_memory`，当 Agent 在不同分支重构时，防止它两次踏入同一条语法/架构河流。
  3. **一个艺术/游戏/叙事方向**：一个“会衰老的解谜游戏 Companion NPC”，它会记住玩家的思维定势并提醒，但如果玩家反复用同一种套路，它会逐渐“遗忘并轻视”这种策略。
- **对我项目的启发**：非常适合与 Drift / 自动化开发流结合。不要只把 memory 当 RAG 数据库，要把 memory 当作一个“自我重构的规则引擎”。
- **今天是否值得深入研究**：是
- **建议行动**：试用（阅读其记忆衰减与更新公式）

## 3. M-Plan: 基于记忆编排的 LLM 长周期任务规划
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2610.27032
- **一句话解释**：通过在上下文窗口外部维持一个动态的“规划-记忆编排板”，解决长程任务（Long-horizon tasks）中状态丢失和目标漂移的问题。
- **它为什么重要**：长周期规划是 LLM 的硬伤。M-Plan 的思路不是给模型更大的 Context，而是把规划状态拆分为“目标状态”、“当前环境投影”、“未决分支”，像流水线一样在外部轮转。
- **技术趋势标签**：#Planning #LongHorizon #AgentWorkflow #StateManagement
- **可复用模式**：**外部化状态机规划（Externalized Blackboard Architecture）** —— 将 Planning 从 LLM 脑中抽离，变成外部黑板（Blackboard），LLM 仅负责阅读黑板切片并更新单个字段。
- **疯狂发明家灵感**：
  1. **一个小实验**：用 Markdown 维护一个严格的看板（Backlog、Active、Done、Blocked），写一个简单的 Python Agent 循环，每次只给它看板的当前 Snapshot，让它自主推进一个 10 步的任务。
  2. **一个中型项目**：世界生成管理系统（Minecraft/网格模拟）：LLM 负责超大地图的历史演进，通过分层外部记忆管理“大陆板块演化 -> 部落兴衰 -> 村落建造”，防止宏观逻辑冲突。
  3. **一个艺术/游戏/叙事方向**：多线分支交互小说引擎：外部黑板记录全宇宙的“关键因果节点”，LLM 玩家无论怎么胡来，系统都通过记忆编排强行计算出符合物理因果的叙事收敛。
- **对我项目的启发**：在设计 Spec-driven 系统时，不要让单次 Prompt 承担全局规划，必须设计一个“状态外置、分片喂入”的运行时架构。
- **今天是否值得深入研究**：是
- **建议行动**：收藏

## 4. Ultimatum Game 中心智理论 (ToM) 与亲社会信念对 Agent 行为的影响
- **来源**：arXiv cs.HC
- **链接**：https://arxiv.org/abs/2505.24255
- **一句话解释**：在经典博弈“最后通牒博弈”中，研究如何给 LLM 注入“猜测对方意图（Theory of Mind）”和“社会道德倾向”，从而让它的博弈行为不再像冷酷的概率机器，而是像真人一样有妥协、愤怒或同情。
- **它为什么重要**：大部分生成式 NPC 都是“被动应答机”，缺乏博弈与谈判深度。这篇文章提供了在极小约束的游戏环境下，如何通过显式 Prompt 架构让 Agent 产生复杂的心理建模和社交张力。
- **技术趋势标签**：#HCI #GameSystems #TheoryOfMind #SocialSimulation #GenerativeAgents
- **可复用模式**：**二阶心智推理提示链（Second-order Belief Prompting）** —— 让 Agent 决策前必须按格式回答：“我认为你认为我会出什么价格”，通过注入这一层镜像投射改变其决策分布。
- **疯狂发明家灵感**：
  1. **一个小实验**：写一个只有 3 轮对话的“二手房东砍价 Agent”，让它实时推理“对方是不是在虚张声势”，并可视化输出其内心的“焦虑/贪婪”浮点值。
  2. **一个中型项目**：一个微型博弈社交沙盒（类似《狼人杀》或小镇模拟）：让 4 个 LLM 在有限资源下分面包，各自拥有不同的 ToM 深度，观察派系形成的涌现行为。
  3. **一个艺术/游戏/叙事方向**：**“读心术神探”解谜游戏**：NPC 拥有显式的欺骗与心智模型。玩家不能直接问出真相，必须通过制造心理压力或利用信息差，诱导 NPC 在 ToM 推理中产生矛盾而自爆破绽。
- **对我项目的启发**：游戏和交互叙事的核心是“张力”。用参数化的 ToM 可以直接做出极具生命力的动态 NPC，而不是千篇一律的维基百科式对话。
- **今天是否值得深入研究**：否（先看结论即可，实验方法很简单）
- **建议行动**：试用（提取其 Prompt 结构）

## 今日模式总结

1. **Proceduralization over Vectorization（技能程序化优于向量化）**：
   从 SPEM 可以看出，向量相似度对于严谨的工作流已经不够用了。将动作、技能、规则组织成带依赖关系的**有向图（Graph/DAG）**，是解决复杂 Agent 任务的确定性趋势。
2. **Meta-Memory & Trace Pruning（元记忆与执行剪枝）**：
   长上下文模型无法解决思维噪点。REM 和 M-Plan 都指向同一个方向：**Agent 必须学会主动把凌乱的思维流（Scratchpad）压缩、总结、并遗忘**，外部沉淀成清洁的状态机。

## 今日可做小实验

### 项目名：Git-Rem: 命令行自愈抗体生成器
- **概念**：基于 REM 和 SPEM 思想，写一个 80 行代码的 CLI 包装器，自动捕获终端报错与修复动作，提炼成代码库专属的“免疫记忆”。
- **输入**：你在终端执行失败的命令及其 stderr，紧接着你成功修复该错误的命令及其 stdout。
- **输出**：在当前目录下生成/追加 `.spec/antibodies.json`（包含：错误模式特征 Regex、原因归纳、推荐动作拓扑）。
- **技术栈**：Python 3 + Rich (终端美化) + 任何轻量 LLM API (GPT-4o-mini 或 Claude 3.5 Haiku) + Subprocess。
- **第一步怎么做**：
  1. 写一个简单的 Python 脚本 `run.py <command>`，用 `subprocess.run(capture_output=True)` 包裹执行你的命令。
  2. 如果 exit code != 0，把错误信息暂存到内存。
  3. 当下一条命令 exit code == 0 时，将“失败输出 + 成功输入”打包发给模型：“请用极其简短的 JSON 输出：1. 这个报错的根本原因；2. 以后避免这个错误的动作规则”。
  4. 追加写入本地 `.spec/antibodies.json`。这就是最原始的结构化抗体记忆。
