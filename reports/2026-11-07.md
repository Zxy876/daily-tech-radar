## 1. Skillware：把 Prompt 炼成确定性可执行“外骨骼”
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2611.07652
- **一句话解释**：主张彻底放弃让 Agent 靠 Prompt 裸猜 API 和手搓代码，提出一套将能力打包为自包含、可审计、确定性执行的“技能软硬件（Skillware）”规范。
- **它为什么重要**：直击当前 Agent 系统的最大痛点——靠动态 Prompt 生成不仅烧 token、吃上下文，而且极其脆弱。将“能力”从“提示词逻辑”剥离成“确定性微容器/标准契约”，是 Agent 工程走向工业级的标志。
- **技术趋势标签**：Agent-as-Code / 确定性执行 / Spec-driven / 模块化工具链
- **可复用模式**：**“装配制而非提示制（Equip, Don't Prompt）”**。Agent 核心只负责路由和调度意图，具体状态流转与 API 约束由固定 Schema 与确定性运行时托管。
- **疯狂发明家灵感**：
  1. **一个小实验**：把一个复杂的个人工作流（如整理日记+打标签+同步Notion）写成一个带严格 JSON-Schema、自带本地单元测试的单文件“Skill 包”，只给 LLM 提供一个该包的 CLI 调用接口。
  2. **一个中型项目**：构建一个面向个人开发者的“Agent 义肢商店（Cyberware for Agents）”，用户像装 Chrome 插件一样给 Cursor 或本地 Agent 挂载经过形式化验证的技能模块。
  3. **一个艺术/游戏/叙事方向**：做一款文字 RPG 引擎，NPC 的性格与能力不是写在 System Prompt 里的文字，而是具象化的“魔导符文（Skillware）”，玩家可以通过偷窃或组合符文，确定性地改写 NPC 的世界交互规则。
- **对我项目的启发**：在设计 Spec-driven 系统或自动化流程时，停止把验证规则塞进上下文，将其抽象成具备前置/后置校验（Pre/Post-condition）的 Skillware 规范。
- **今天是否值得深入研究**：是
- **建议行动**：做demo

## 2. Cross-Agent Dafny Formalization：规格制定者与实现者的对抗博弈
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2611.07073
- **一句话解释**：提出了一个“双 Agent + Dafny 形式化验证”协议：Specifier Agent 负责将需求翻译成 Dafny 谓词规格，Implementer Agent 编写代码，再通过数学证明器自动验证两者是否一致。
- **它为什么重要**：解决了 Spec-driven development 最核心的信任危机——LLM 自己写代码、自己写测试往往会“自圆其谎”（Verification is not Agreement）。通过逻辑形式化语言 Dafny 隔离“规则制定”与“代码实现”，实现了真正的机器自洽闭环。
- **技术趋势标签**：形式化验证 / Spec-driven / 多智能体博弈 / 符号AI与LLM结合
- **可复用模式**：**“双盲规范校验器（Specifier-Implementer Split）”**。让 Agent A 只读需求产出断言（Contracts），Agent B 只看断言写实现，由形式化编译器当无私裁判。
- **疯狂发明家灵感**：
  1. **一个小实验**：用两个 Claude 会话，A 专门把一段自然语言游戏规则写成 Python `assert` 逻辑或 Pydantic 模型，B 专门写游戏逻辑，跑通过即判定成功，观察能拦截多少隐性 bug。
  2. **一个中型项目**：开发一个“无谎言代码生成器”，支持针对数据处理流水线自动生成 Dafny/Z3 形式化契约，确保清洗和变换逻辑数学级正确。
  3. **一个艺术/游戏/叙事方向**：设计一个“律法世界解谜游戏”。世界被一组严格的形式化规则约束（如“重力不可逆”、“时间单向流动”），玩家通过 Agent 去世界法典里找逻辑漏洞（Proof Hole），利用规则冲突引发“物理引擎故障”来通关。
- **对我项目的启发**：极其切中 Spec-driven 的灵魂。Spec 不该是自然语言文档，必须是“不可抵赖的机器断言”，开发 Agent 的核心目标是缩小 Spec 与 Code 的语义漂移。
- **今天是否值得深入研究**：是
- **建议行动**：做demo

## 3. CST-Bench：让多模态模型推演“如果我推倒这块多米诺骨牌”
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2611.07541
- **一句话解释**：首个针对 MLLM（多模态大模型）在物体被移动、替换等空间干预下，测试其对“动态因果空间状态转移（Counterfactual Spatial Transition）”推演能力的评测基准与蒸馏方法。
- **它为什么重要**：现有视觉模型大多只具备静态感知能力（“图里有什么”），却无法在脑海中运行“物理世界状态机”（“若把A挪到B上面，C会不会塌”）。这是让 AI 参与 3D 游戏设计、Minecraft 自动化搭建和物理交互的核心瓶颈。
- **技术趋势标签**：空间智能（Spatial AI） / 世界模型（World Models） / 因果推理 / 游戏生成系统
- **可复用模式**：**“因果图空间状态追踪（Causal Transition Tracking）”**。不再让模型把场景视为像素序列，而是将空间抽象为由物理接触和位置关系构成的动态图谱，根据动作做图重写。
- **疯狂发明家灵感**：
  1. **一个小实验**：构建一个基于 ASCII/网格的简单 Minecraft 积木房间，给 GPT-4V 发送一张图并提问：“如果移除方块 [2, 3]，哪几个方块会因为失去重力支撑掉落？”，测试当前模型的物理推断上限。
  2. **一个中型项目**：做一个 Minecraft / 3D 场景的“因果建造助手”——你在前端拖放方块，Agent 实时推演结构稳定性，并在空中投射虚幻的“应力崩塌预测轨迹”。
  3. **一个艺术/游戏/叙事方向**：一个“不可逆因果迷宫”生成器。玩家输入故事梗概，系统生成一个每个动作都会彻底摧毁/重构局部拓扑的关卡，叙事线索与物理坍塌完全绑定。
- **对我项目的启发**：在做世界生成与自动化系统时，必须引入“世界状态差分器（State Diff Engine）”，不能依赖纯 Vision-LLM 脑补物理，需用轻量状态机辅助其因果推理。
- **今天是否值得深入研究**：是
- **建议行动**：试用

## 4. Timbre Agency：生成式界面里“伪造”的坐标系与机器自主性
- **来源**：arXiv cs.HC
- **链接**：https://arxiv.org/abs/2610.12532
- **一句话解释**：揭露了当前生成式创意界面中一个荒诞的 HCI 现象：界面上呈现给创作者的“声音/设计潜空间坐标”，往往不是从真实数据计算出的物理量，而是 LLM“脑补描述”出来的虚拟幻觉，探讨由此引发的虚假控制感。
- **它为什么重要**：站在艺术、设计与 HCI 的交叉点，反思了我们日常用的“AI 调色盘/潜空间滑块”到底是工具还是幻象。对于做 Creative Tool 的人，这直接颠覆了传统的 UI/UX 映射哲学。
- **技术趋势标签**：HCI / 创意工具（Creative Tools） / 潜空间可视化 / 批判性设计（Critical Design）
- **可复用模式**：**“幻觉界面的反讽与重构（Perceptual Discrepancy UI）”**。显式地区分系统“测得的属性（Ground Truth）”与模型“宣称的属性（Model Imagination）”，并利用这种落差作为创意媒介。
- **疯狂发明家灵感**：
  1. **一个小实验**：做一个 p5.js / Web 界面，界面上有两个二维探索点：一个映射真实的音频 FFT 特征，一个映射 LLM 对音乐情感的形容词向量，把它们连成弹簧，让用户看“声学事实”与“AI 审美偏见”之间的拉扯。
  2. **一个中型项目**：开发一个面向声音设计师的“反直觉音色发生器”，故意暴露并放大 LLM 语义与 DSP 声音合成器之间的空间畸变，让创作者在“不可控的缝隙”中捕获灵感。
  3. **一个艺术/游戏/叙事方向**：制作一个装置或网页互动体验——《虚假坐标系制图师》。玩家在一个看似精确的地图界面上点击探索，系统一步步揭露地图上的山川经纬全部是语言模型根据上一句话编造出来的“自洽假象”。
- **对我项目的启发**：做生成式创作工具时，不要做传统的“伪控制滑块”。要么给创作者 100% 确定性的结构化手柄，要么就坦率地把 AI 的“不可控性”戏剧化，变成一种生成式审美体验。
- **今天是否值得深入研究**：是
- **建议行动**：收藏

## 今日模式总结

1. **去 Prompt 化，走向确定性契约（From Prompt to Contract）**：从 Skillware 到 Dafny 验证，行业正在对自然语言 Prompt 的脆弱性产生审美疲劳，将能力封装为严苛规范、用数学工具/执行容器兜底正在成为硬核工作流的共识。
2. **因果与物理状态的显式化建模（Explicit State vs. Implicit Hallucination）**：无论是 3D 空间反事实推理，还是音色生成的 HCI 界面反思，都在强调：模型内部隐式表征不可信，必须构建显式的状态机（State Machine）或感知校准层。

## 今日可做小实验：2小时原型

- **项目名**：Contract-Craft（基于前置/后置条件的方块状态转移器）
- **输入**：一段自然语言动作（例如：“把底座右侧的金块拆下来，塞到左侧漂浮的石阶下方”） + 当前空间 JSON 网格状态。
- **输出**：
  1. 形式化 Spec（包含 `precondition`: 方块是否存在；`postcondition`: 重力校验及新坐标）；
  2. 验证后的有效下一帧世界状态（或阻断报错及原因）。
- **技术栈**：Python + Pydantic + 简易 3D/ASCII 打印脚本 + 任意 LLM API（通过 JSON 模式输出）。
- **第一步怎么做**：
  用 Pydantic 写两个数据类：`WorldState`（一个 5x5x5 的空间字典）和 `ActionSpec`（包含 `action_type`, `target_coord`, `pre_conditions: List[str]`）。让 LLM 只负责把自然语言指令解析成 `ActionSpec`，随后由本地 Python 解释器执行判定，验证它是否比直接让 LLM 猜“接下来方块在哪”更稳定可靠。
