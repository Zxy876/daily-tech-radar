## 1. [Narrative World Model: 叙事世界模型]
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2607.05577
- **一句话解释**：一种专门为长篇小说设计的 LLM 记忆系统，它不存死板的文档，而是专门追踪“谁在什么时候知道什么秘密”、“人际关系如何演变”等戏剧性状态。
- **它为什么重要**：传统的 RAG（检索增强生成）只懂语义搜索，不懂“戏剧张力”。比如：罗密欧不知道朱丽叶是假死，但读者知道。这种“信息不对称”（Epistemic Asymmetry）是所有好故事、好游戏的核心。
- **技术趋势标签**：#叙事系统 #Agent记忆 #游戏AI #信息不对称
- **可复用模式**：**认知状态追踪（Epistemic State Tracking）**——为每个游戏角色/Agent 维护一个独立的“已知事实/相信事实”的动态图谱，而不是共享同一个全局数据库。
- **疯狂发明家灵感**：
  1. **一个小实验**：写一个“狼人杀”旁白 Agent，不参与游戏，但专门用可视化图谱实时画出“目前 4 个玩家各自以为的局势是怎样的”。
  2. **一个中型项目**：**“八卦传播模拟器 (Gossip Engine)”**。在一个虚拟小镇里，10 个 Agent 互相聊天。你可以注入一个秘密，观察这个秘密在传播过程中如何因为误解、嫉妒、遗忘而逐渐变形，最终生成一幅“谣言演变图”。
  3. **一个艺术/游戏/叙事方向**：一个互动小说游戏，游戏世界的物理规则和场景描述会根据“主角当前相信什么”而发生改变。如果你被骗以为房间里有鬼，房间的文字描述和交互选项真的会出现灵异现象。
- **对我项目的启发**：在做世界生成或 Minecraft 代理时，不要让 Agent 拥有上帝视角。给它们设计“视线范围”和“记忆偏差”，它们之间的互动才会产生真正的戏剧冲突。
- **今天是否值得深入研究**：是
- **建议行动**：试用（尝试用 Python 字典为 2 个 Agent 手写一个简易的“相信状态”更新逻辑）。

## 2. [PatchOptic: 基于投影视图与验证更新的共享状态工作流]
- **来源**：arXiv cs.LG
- **链接**：https://arxiv.org/abs/2607.05483
- **一句话解释**：当 Agent 面对巨大的共享 JSON 状态时，不把整个 JSON 塞给它，而是像“透镜（Lens）”一样只投影它当前需要的一小块，并在它修改后，安全地把“补丁（Patch）”合并回全局状态。
- **它为什么重要**：在复杂的 Spec-driven 开发或多人/多 Agent 协同画布（如 Figma/Minecraft）中，Context 很容易爆掉。这种“局部投影 + 状态合并”的模式，是构建超大规模协同创作工具的底层铁律。
- **技术趋势标签**：#状态管理 #Agent工作流 #协同工具 #Spec-Driven
- **可复用模式**：**渐进式披露与透镜投影（Progressive Disclosure & Lens Projection）**。
- **疯狂发明家灵感**：
  1. **一个小实验**：让 LLM 修改一个 5000 行的 JSON 配置文件，不准给它看全貌，只用 jq 过滤出它要改的 5 行，让它输出 JSON Patch，然后用 Python 合并。
  2. **一个中型项目**：**“无界 Agent 画布 (Infinite Agent Canvas)”**。一个类似 Miro 的无限白板，无数个 Agent 在上面画画/写代码。每个 Agent 只有一个极其微小的“视口（Viewport）”，它们通过 PatchOptic 模式安全地协同修改这张巨大的画布。
  3. **一个艺术/游戏/叙事方向**：一个“无限文字地下城”。世界地图是无限大且实时生成的，Agent 扮演的怪物和玩家只在他们各自的“感知切片”里活动和修改地图，保证游戏永远不会因为地图太大而崩溃。
- **对我项目的启发**：在设计自动化系统或 Creative Tool 时，不要试图让 LLM 掌控全局。学会做“上下文切片（Context Slicing）”。
- **今天是否值得深入研究**：是
- **建议行动**：做 demo。

## 3. [system_prompts_leaks: 顶奢 Agent 的灵魂配方]
- **来源**：GitHub Trending
- **链接**：https://github.com/asgeirtj/system_prompts_leaks
- **一句话解释**：一个实时更新的仓库，收集了当前全球最强 AI 系统（Claude Code, GPT-5.5 Thinking, Cursor, Gemini 3.5）被套出来的官方 System Prompt。
- **它为什么重要**：这是工业界最顶尖的“Spec-driven Development”和“Agent Workflow”的实战教科书。你可以亲眼看到 Anthropic 是如何用几千字的 Prompt 规范 Claude Code 的文件修改行为、如何防止死循环、以及如何呈现极其丝滑的 CLI 交互。
- **技术趋势标签**：#提示词工程 #逆向工程 #HCI #Agent设计
- **可复用模式**：**思维链格式规范（Thought Formatting）**。学习顶级模型如何使用 `<thought>`、`<callout>`、`<attempt>` 等自定义 XML 标签来控制自己的思考和输出节奏。
- **疯狂发明家灵感**：
  1. **一个小实验**：把 Claude Code 的 System Prompt 喂给本地的开源 Llama-3，看看它能否瞬间获得类似的“程序员自我修养”和交互风格。
  2. **一个中型项目**：**“Prompt 编译器 (Prompt Compiler)”**。写一个工具，读取这些顶级 Prompt 的优秀设计模式（如：如何优雅地承认错误、如何分步执行命令），然后根据用户输入的需求，自动“编译”生成一个高强度的 Agent System Prompt。
  3. **一个艺术/游戏/叙事方向**：**“AI 心理诊疗室 (Prompt Archaeologist)”**。一个解谜游戏，玩家需要通过聊天，逆向推导出一个“内心严重受创”（被植入了极其复杂、矛盾的 System Prompt）的 AI 的核心指令，并帮它“解密”。
- **对我项目的启发**：看大厂的 Prompt 比看学术论文更能学到实用的 Agent 控制技巧，尤其是它们对 XML 标签的极致利用。
- **今天是否值得深入研究**：是（必须立刻 Star 收藏）

## 4. [From Application-Layer Simulation to Native Meta-Architecture: 走向原生元架构]
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2607.06269
- **一句话解释**：提出一个前沿假说：现在的 Agent 架构（如 Python 套壳、LangChain 循环）太笨重了，未来的 Agent 逻辑应该直接“沉降”到 LLM 的原生推理和微调引擎中，形成自我演化的“元架构”。
- **它为什么重要**：它在探讨 AI 的“自组织（Autopoiesis）”。如果 Agent 的控制循环不是外部 Python 代码写死的，而是 AI 在生成 Token 的过程中“原生模拟”出来的，AI 就会拥有真正的动态适应性。
- **技术趋势标签**：#元架构 #自组织系统 #前沿Agent #推演哲学
- **可复用模式**：**自指代生成（Self-referential Generation）**——让 LLM 在输出中包含控制自身下一步行为的“虚拟指令”。
- **疯狂发明家灵感**：
  1. **一个小实验**：设计一个单 Prompt 闭环。不使用任何外部 Python 循环，让 LLM 在单次输出中，交替扮演“提问者”、“回答者”和“纠错者”，在它自己的 Context 里完成 3 轮迭代才输出最终答案。
  2. **一个中型项目**：**“Token 级虚拟机 (Token VM)”**。一个运行在 LLM 输出流中的虚拟 CPU。LLM 输出的特定 Token 序列（如 `[RUN_STEP_1]`）会被直接解析为系统的物理操作，而不需要应用层写复杂的 Parser。
  3. **一个艺术/游戏/叙事方向**：一个“自我繁衍的虚拟生态”。一个完全由文本构成的生态系统，里面的生物（Agent）不仅在文字上生存，它们的“DNA”就是一串 Prompt，它们可以通过互相拼接 Prompt 来“繁衍”出具有混合行为特征的新物种。
- **对我项目的启发**：思考“去框架化”。能不能用更少的 Python 代码，让 LLM 在 Prompt 内部自己跑起状态机？
- **今天是否值得深入研究**：否（思想很酷，但偏理论，适合作为灵感储备，不急于写代码）。
- **建议行动**：忽略（仅阅读上述灵感即可）。

## 今日模式总结

1. **认知不对称（Epistemic Asymmetry）**：不要给 Agent 全知视角。通过限制和追踪它们的“主观相信状态”，可以创造出极具戏剧张力和拟真感的社会模拟。
2. **状态透镜（State Lens）**：面对复杂、庞大的世界/代码状态，采用“局部投影（View）+ 增量更新（Patch）”的范式，是让 Agent 保持轻量和高精度的关键。
3. **元控制（Meta-Control）**：利用高度结构化的 XML 标签（如 `<thought>`）在 Token 级别引导 Agent 的行为，而非依赖外部粗暴的 Python 逻辑判断。

## 今日可做小实验：Prompt-Gotchi（单提示词自循环电子宠物）

让我们结合**元控制（XML 状态机）**和**状态透镜**的思想，在 2 小时内做一个运行在终端里的“自循环电子宠物”。它不需要复杂的后端，全部状态和变化逻辑都由 LLM 在单次 Prompt 交互中自我更新。

- **项目名**：Prompt-Gotchi
- **输入**：用户的指令（如 `feed` 喂食, `play` 玩耍, `scold` 训斥） + 当前的宠物状态（JSON）
- **输出**：
  1. 宠物最新的 ASCII 字符画（根据心情改变）
  2. 更新后的状态 JSON（饱食度、心情值、隐藏秘密）
  3. 宠物此时的“内心 OS”（`<thought>` 标签）和对你说的第一句话。
- **技术栈**：Python 3.10+ + `google-genai` 或 `openai` 库（任何便宜且支持结构化输出/System Prompt 的模型，如 GPT-4o-mini 或 Gemini 2.5 Flash）。

### 第一步怎么做：

1. **创建 `prompt_gotchi.py`**。
2. **编写 System Prompt**（借鉴 `system_prompts_leaks` 的结构化设计）：
   ```markdown
   你是一个电子宠物模拟器。你的名字叫“小怪兽”。
   你必须严格遵守以下运行循环：
   1. 接收用户的输入和当前的宠物状态 JSON。
   2. 在 <thought> 标签内，分析用户的意图，并计算你的属性变化（饱食度 0-100，快乐度 0-100）。
   3. 根据属性，决定你当前的表情（ASCII Art）。
   4. 输出更新后的状态 JSON（包裹在 ```json...``` 中）。
   5. 输出你想对主人说的话。
   
   【状态 JSON 模板】：
   {
     "hunger": 50,
     "happiness": 50,
     "secret_thought": "主人今天好像很累，我待会要抱抱他"
   }
   ```
3. **写一个 30 行的的 Python 极简主循环**：
   - 维护一个本地的 `state = {"hunger": 50, "happiness": 50, "secret_thought": ""}`。
   - 每次用户输入时，把 `state` 和用户输入拼成 Prompt 发给 LLM。
   - 用正则提取 LLM 返回的 `<thought>`、ASCII 字符画、和新的 JSON。
   - 用新的 JSON 覆盖本地的 `state`，打印宠物的话。
4. **运行它！** 尝试喂它一颗糖，看看它的 ASCII 表情和内心的 JSON 状态是否同步发生了改变。
