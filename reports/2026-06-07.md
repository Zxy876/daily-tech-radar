## 1. Brick-Composer: Using MLLMs for Assembly with Diverse Bricks
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2606.05445
- **一句话解释**：研究如何让多模态大模型（MLLM）像人类看说明书拼乐高一样，通过视觉识别和空间推理，一步步用基础积木（Bricks）拼装出复杂的三维物体。
- **它为什么重要**：它打通了“2D视觉/设计意图”与“3D空间离散化拼装”之间的通道。对于喜欢 Minecraft、体素（Voxel）艺术和生成式系统的你来说，这是将 AI 引入物理/虚拟世界建造的完美桥梁。
- **技术趋势标签**：#MLLM #空间推理 #体素生成 #HCI
- **可复用模式**：`目标图像 -> MLLM 空间分解 -> 离散积木序列化步骤（x, y, z, block_type） -> 渲染/建造`。
- **疯狂发明家灵感**：
  1. **一个小实验**：写一个 Python 脚本，输入一张极简的像素画，让 GPT-4o 输出对应的 Minecraft `/setblock` 指令序列，在游戏里自动盖出这个图案。
  2. **一个中型项目**：**"AI-Lego-Sculptor"（AI 乐高雕塑家）**。用户上传任意 3D 模型的照片，AI 代理（Agent）在 WebGL 页面中实时、一步步地用虚拟乐高积木将其拼装出来，并在拼装过程中向用户解释它的“力学和美学考量”。
  3. **一个艺术/游戏/叙事方向**：**《巴别塔的盲眼建筑师》**。一个双人协作游戏：人类玩家扮演“设计师”（只能画草图），AI 扮演“盲眼建筑师”（只能理解空间坐标和积木）。AI 必须通过理解人类的草图，在虚拟世界中建造一座不断长高的城堡，玩家需要通过文字纠正它的空间偏差。
- **对我项目的启发**：在做世界生成或 creative coding 时，不要让 LLM 直接生成复杂的 3D Mesh，而是让它生成**“离散的装配指令”**。这极大地降低了模型的推理难度，且天然具备极高的人机交互性。
- **今天是否值得深入研究**：是
- **建议行动**：做demo

## 2. Mutation Without Variation: Convergence Dynamics in LLM-Driven Program Evolution
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2606.05408
- **一句话解释**：论文发现，当让 LLM 反复迭代/突变一段代码（且不施加任何外部筛选压力）时，代码并不会无限发散，而是会收敛到某些特定的、稳定的“吸引子（Attractor）”状态。
- **它为什么重要**：揭示了 AI 自动编程的“重力场”。在 Spec-driven development（规范驱动开发）中，如果你让 AI 自由发挥，它会陷入某种思维死胡同。理解这个“收敛动力学”，我们就能设计出“反收敛”的机制，逼迫 AI 保持创造力。
- **技术趋势标签**：#代码演化 #Spec-driven #生成艺术 #数字生态
- **可复用模式**：`代码 -> LLM 突变 -> AST（抽象语法树）哈希对比 -> 检测收敛 -> 注入对抗性扰动`。
- **疯狂发明家灵感**：
  1. **一个小实验**：写一个链式突变脚本。输入一段简单的 Canvas 绘图代码，让 LLM 连续突变 20 代（“微调这段代码，让画面更丰富”），观察它的视觉效果最终是稳定在某个图案，还是彻底崩溃。
  2. **一个中型项目**：**"Synthetic Code Ecologies"（合成代码生态缸）**。在网页里运行多个“代码生物”（比如用 p5.js 写的自主移动的 Agent），它们的行为代码由 LLM 控制。当它们碰撞时，代码会发生“有性繁殖/突变”。引入“环境灾变”来打破论文中提到的“无变异收敛”，观察代码物种的演化。
  3. **一个艺术/游戏/叙事方向**：**《失控的编译器》**。一个解谜游戏，玩家需要在一座废弃的 AI 空间站里，通过向一个不断自我突变、逐渐僵化的 AI 核心注入“逻辑病毒”（对抗性 Prompt），迫使它突变出新的功能代码来帮你开门。
- **对我项目的启发**：在设计自动化 Agent 工作流时，如果发现 Agent 的输出越来越单一，说明系统陷入了“吸引子”。必须引入类似“退火算法”的随机性，或者在 Prompt 中强制加入“禁止使用的模式”（Negative Specs）。
- **今天是否值得深入研究**：是
- **建议行动**：试用（跑一个 10 代的代码突变实验）

## 3. What Should Agents Say? Action-state Communication for Efficient Multi-Agent Systems
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2606.05304
- **一句话解释**：研究指出，多特工系统（MAS）中让 Agent 用大白话（自然语言）聊天太浪费 Token 且容易跑题，应该让他们使用结构化的“动作-状态（Action-State）”协议进行高效、高密度的通信。
- **它为什么重要**：解决了多 Agent 协同中的“废话文学”问题。对于游戏系统设计、NPC 社交模拟、以及自动化开发工作流，这套协议能让 Agent 运行速度提升数倍，成本降低 90%。
- **技术趋势标签**：#多特工系统 #通信协议 #游戏系统 #Agent工作流
- **可复用模式**：`Agent A 发送状态 JSON -> Agent B 更新世界状态 -> Agent B 做出动作决策`（用极简 JSON 替代 Natural Language Chat）。
- **疯狂发明家灵感**：
  1. **一个小实验**：用 Python 写两个正在下棋或合作解谜的 Agent，限制它们只能通过特定的 JSON 格式（例如 `{ "status": "thinking", "action": "move_to", "target": [3, 4] }`）交流，不准说一句废话，测试其任务完成率。
  2. **一个中型项目**：**"The Silent Voxel Town"（静默体素小镇）**。在网页端运行一个 3D 模拟小镇，里面的 AI 居民（矿工、木匠、商人）通过底层的 Action-State 协议进行资源交易和建筑规划，前端将他们的“无声通信”可视化为头顶流动的彩色数据线。
  3. **一个艺术/游戏/叙事方向**：**《无声合唱》**。一个声音装置艺术。三个 AI 歌手 Agent，它们不能听到对方的声音，只能通过极低带宽的“情感状态码”协议进行通信。它们需要根据对方传输的“张力值”和“和谐度”来调整自己的音高，最终合奏出一首随机但和谐的交响乐。
- **对我项目的启发**：在构建复杂 Agent 链时，戒掉“让 Agent 互相写信（自然语言）”的习惯。为它们设计一套 Spec-driven 的微型通信协议（Schema），这才是工业级 Agent 系统的未来。
- **今天是否值得深入研究**：是
- **建议行动**：做demo

## 今日模式总结

今天我们捕获了 3 个核心技术模式：
1. **空间装配序列化（Spatial Assembly Serialization）**：将复杂的 3D 生成问题降维转化为 MLLM 易于理解的“离散积木拼装步骤”，极适合游戏和 creative coding。
2. **代码吸引子动力学（Code Attractor Dynamics）**：认识到 LLM 自动编程存在“自然收敛/僵化”的特性，在设计生成式系统时必须主动引入“变异扰动”。
3. **状态-动作协议化（State-Action Protocolization）**：在多 Agent 系统中，用高密度的 JSON 协议取代低效的自然语言对话，实现低成本、高并发的 Agent 协同。

## 今日可做小实验：代码降级观测器 (Code Degenerator)

利用 **Candidate 14** 的理论，我们来做一个 2 小时内的代码演化小实验，亲眼观察 LLM 代码突变的“收敛吸引子”。

- **项目名**：Code Degenerator & Attractor Mapper
- **输入**：一段标准的、可运行的 JavaScript 绘图代码（比如用 Canvas 画一个旋转的彩色五角星）。
- **输出**：一个 HTML 页面，左边是原始代码和第 10 代、第 20 代突变后的代码，右边是它们运行出来的 Canvas 视觉效果对比图，以及每次突变的相似度曲线。
- **技术栈**：Node.js + HTML + Anthropic Claude API (或 OpenAI GPT-4o-mini)
- **第一步怎么做**：
  1. 准备好你的 API Key，新建一个 Node.js 项目并安装 `@google/generative-ai` 或 `openai`。
  2. 写一个初始的 `initial_code.js`，里面包含一个在 `<canvas>` 上画图的自执行函数。
  3. 编写 Prompt：
     > "你是一个代码变异器。请对以下 JavaScript Canvas 绘图代码进行微小的、随机的修改（例如改变颜色、旋转速度、线条粗细或几何算法），但必须保持其在 Canvas 上有视觉输出且无语法错误。直接输出修改后的代码，不要任何 Markdown 标记和解释。"
  4. 写一个 Loop 循环，把初始代码丢给 LLM，拿到输出后写入 `generation_1.js`；然后把 `generation_1.js` 作为输入再丢给 LLM，循环 10 次。
  5. 编写一个极简的 HTML 页面，用 `<iframe>` 或直接把这 10 代代码动态 `eval()` 运行在画布上，看看它们最终是变成了一团乱麻，还是收敛成了一个极其简单的“单色圆点”（收敛状态）。
