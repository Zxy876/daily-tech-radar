## 1. SPEM: Structure-Aware Procedural Memory for LLM Agents
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2610.26995
- **一句话解释**：抛弃把 Agent 技能当扁平文本检索的做法，改用保留“依赖、执行序、状态转移和数据流”的结构化程序记忆。
- **它为什么重要**：长任务 Agent 积累了几百个 Skill 后，向量检索（RAG）经常找错或丢掉依赖项。把“技能库”升级为“状态机/拓扑图”，是复杂 Agent 从玩具走向工程执行的关键分水岭。
- **技术趋势标签**：#ProceduralMemory #AgentSkills #GraphExecution #SpecDriven
- **可复用模式**：**有向无环技能图（Skill-DAG）**——技能不是 prompt 片段，而是带明确前置条件（Preconditions）、输入输出类型契约、回滚路径的状态节点。
- **疯狂发明家灵感**：
  1. *小实验*：给本地 Claude Code / Agent 写一个技能拓扑，用 JSON 描述技能依赖，强制 Agent 执行 `skill_B` 前必须校验 `skill_A` 的产物。
  2. *中型项目*：**Drift 自动化构建管线**：让代码生成 Agent 不再“边想边写”，而是先基于 Spec 组装出技能状态机（如：拉取规范 -> 生成接口 -> 跑测试 -> 修复），带依赖校验执行。
  3. *艺术/游戏/叙事方向*：**Minecraft 复杂红石/建筑蓝图编译 Agent**。将建筑拆解为严格依赖的结构化程序（如地基 -> 承重 -> 封顶 -> 装饰），Agent 会根据地形动态推演依赖树并执行建造。
- **对我的项目的启发**：在 Spec-driven 开发中，Spec 实际上就是这种程序性记忆的根节点。可以把规范定义为可执行的状态依赖图。
- **今天是否值得深入研究**：是
- **建议行动**：做demo

## 2. WhatIf: Interactive Exploration of Large-Scale Agent Simulations
- **来源**：arXiv cs.HC
- **链接**：https://arxiv.org/abs/2604.17615
- **一句话解释**：一个为人机交互决策设计的界面系统，让人类能交互式干预、分支探索并可视化大规模 LLM Agent 模拟演进。
- **它为什么重要**：从斯坦福小镇（Generative Agents）以来，多 Agent 模拟一直缺乏“交互式推演”的 HCI 介质。它填补了“黑盒模拟”与“人类直觉干预”之间的交互空白。
- **技术趋势标签**：#HCI #AgentSimulation #WorldBuilding #GameSystems
- **可复用模式**：**时间线分支与反事实干预（Counterfactual Forking）**——允许在时间轴任意一点暂停世界、注入新变量、派生并行世界线对比结果。
- **疯狂发明家灵感**：
  1. *小实验*：用 Python + SQLite 记录 5 个 Agent 的对话状态机，做一个网页滑块，随时回退到第 3 轮修改某个 Agent 的信念（Belief），观察后续演化差异。
  2. *中型项目*：**叙事推演设计台（Story Weaver Sandbox）**：游戏编剧或关卡策划可实时向虚拟小镇广播谣言或天气突变，仪表盘实时聚类 Agent 的群体动态。
  3. *艺术/游戏/叙事方向*：**互动生成式生态戏剧**：在虚拟空间（如 Minecraft 或 3D 网页环境）里投放拥有不同信仰的 NPC，观众通过打字实时投掷“神迹/灾难”，系统动态渲染世界线分支图。
- **对我的项目的启发**：做世界生成或游戏系统时，UI 不应只是静态展示，应该作为“时间线分叉控制器”。
- **今天是否值得深入研究**：是
- **建议行动**：收藏（重点看其 HCI 交互界面与状态分支控制的设计逻辑）

## 3. REM: What to Store, Recall, and Forget in Coding Agent Memory
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2610.27377
- **一句话解释**：打破“被动相似度检索”的静态记忆模式，构建能监控 Agent 实时执行流并主动决定“何时存、何时调、何时遗忘”的代码经验记忆系统。
- **它为什么重要**：Agent 经常在遇到曾经踩过的坑时再次翻车。静态向量库不仅噪音大，还会误导 Agent。提出“主动式遗忘与提取”是让自主 Agent 越跑越聪明的刚需技术。
- **技术趋势标签**：#MemoryPruning #AutonomousCoding #SelfReflectingAgent
- **可复用模式**：**运行感知型经验过滤器（Runtime-Aware Memory Gate）**——记忆不是存整个对话历史，而是只提取“错误签名（Error Signature）-> 解决尝试 -> 最终有效 Fix”的最小差分闭环，其余全部丢弃。
- **疯狂发明家灵感**：
  1. *小实验*：写一个 Git pre-commit hook 或本地拦截脚本，捕获你的终端报错和最终修好的 `git diff`，自动精简为一行规则写入本地 `.agent_tips`。
  2. *中型项目*：**自愈型 Spec 执行器**：在运行测试报错时，Agent 自动查询过去的“错误模式库”，并在任务成功后将死胡同（Dead-ends）主动打上“避坑标签”。
  3. *艺术/游戏/叙事方向*：**带“肌肉创伤记忆”的游戏 NPC 战斗系统**：NPC 不记录整局战斗，只记录死前 3 秒的操作漏洞，复活后主动修剪无关记忆，只保留针对玩家特定招式的反制策略。
- **对我的项目的启发**：给自己的 Agent 工具链做 memory 时，不要无脑丢向量数据库，先做上下文轻量化和“遗忘机制”。
- **今天是否值得深入研究**：是
- **建议行动**：试用（提取其 Memory 过滤逻辑到自身工作流中）

## 4. Teaching AI Agent to Play Poker Strategically Through Preference Optimization
- **来源**：arXiv cs.AI
- **链接**：https://arxiv.org/abs/2610.27028
- **一句话解释**：利用偏好对齐（DPO/PO）训练极小体量的大模型（如 SmallThinker/Qwen3），在不完全信息博弈（德州扑克）中展现出“虚张声势（Bluffing）”等高级战略行为。
- **它为什么重要**：证明了不用百亿大模型、不需要极重的强化学习框架，小参数模型通过“博弈轨迹的偏好对比”，也能学会欺骗、试探、博弈。这为轻量化、边缘运行的“高智商游戏 NPC”铺平了路。
- **技术趋势标签**：#IncompleteInformation #GameAI #CompactLLM #PreferenceOptimization
- **可复用模式**：**非完全信息行为的偏好配对（Trajectory DPO）**——将“保守直白的动作”作为劣解，将“带伪装与心理博弈的动作”作为优解，微调小型语言模型。
- **疯狂发明家灵感**：
  1. *小实验*：构建一个狼人杀/阿瓦隆最小上下文，给 3B 本地模型喂两组对话（一组直接招供，一组言语诱导），观察微调后小模型是否学会转移怀疑。
  2. *中型项目*：**极低延迟的本地游戏 NPC 决策引擎**：用 Ollama 跑量化的 3B 模型，驱动策略游戏里的敌人，使其具备藏牌、声东击西等策略行为，不消耗云端 API。
  3. *艺术/游戏/叙事方向*：**“不可靠叙述者”互动小说**：游戏内的 NPC 全身都是“隐藏信息”，通过偏好优化让它表面顺从玩家，暗中布局背叛，给玩家带来真正的心理博弈震慑。
- **对我的项目的启发**：游戏和叙事系统里的 AI 拟人性，不在于“能背诵多少维基百科”，而在于“信息差管理”和“欺骗/试探的策略感”。
- **今天是否值得深入研究**：否（不需要深挖 RL 公式，重点吸收其构建博弈偏好数据的思路）
- **建议行动**：收藏

## 今日模式总结

1. **结构化超越扁平向量（Structure over Semantic Vectors）**：从 SPEM 到 REM，都在反思“暴力 RAG”，Agent 记忆正全面转向具备拓扑关系、状态机和明确数据流的有向图。
2. **记忆的主动新陈代谢（Active Memory Metabolism）**：“存什么”不再关键，“删什么”和“何时触发”成为瓶颈，负反馈与错误死胡同（Dead-ends）比正确答案更有压缩价值。
3. **人类对复杂模拟的掌控介质（Interactive Sandbox HCI）**：随着自主多 Agent 系统的蔓延，产品与设计重点转向“反事实推演界面（Counterfactual UI）”，即人类如何作为“时空观测者”去分支、回溯与干预。

## 今日可做小实验（2小时极速版）

### 🧪 项目名：**GitDiff-Reflector（Agent 极简错误自愈与遗忘记忆器）**

- **输入**：一段报错信息（Terminal Error Log） + 修复后的代码差异（`git diff`）。
- **输出**：一条极简格式的 YAML 规则，记录：`{ trigger_error: "...", forbidden_action: "...", correct_recipe: "..." }`。
- **技术栈**：Python / Node.js + LiteLLM（调用任意模型） + Git 本地仓库。
- **第一步怎么做**：
  1. 在你最近的一个小项目根目录下写一个 `remember.py`。
  2. 运行 `git diff HEAD~1` 获取最后一次成功修复代码的 diff。
  3. 让 LLM 做一个单步任务：“不要生成解释，提取该 diff 解决的核心错误类型，并只输出一条包含【禁止动作】和【正解】的 100 字内规则”。
  4. 追加写入本地 `.agent_rules.yaml`，并在下次唤起编程 Agent 的 System Prompt 中直接注入该文件。立即体验“主动经验沉淀”！
