## MirrorCraft: Minecraft 中隐性规则变更下的 LLM Agent 适应性评估
- 来源：arXiv cs.AI
- 链接：https://arxiv.org/abs/2607.29218
- 一句话解释：评估当 Minecraft 底层物理/合成规则被“偷摸修改”时，LLM Agent 能否通过探索重新发现规律并适应。
- 它为什么重要：现在的 Agent 多数依赖死记硬背的固化 SOP。真实世界和好游戏都充满了动态变量，真正的灵智在于“发现世界规则变了，并主动建立新认知”。
- 技术趋势标签：#Minecraft #Worldgen #AgentAdaptation #DynamicGameRules #EmergentBehavior
- 可复用模式：**规则篡改与探索反馈循环 (Rule-Mutation & Discovery Loop)**：通过隐性篡改系统参数，逼迫 Agent 从“执行现有规程”切换为“假设-实验-验证”的科学探索模式。
- 疯狂发明家灵感：
  1. **一个小实验**：写一个简单的网格迷宫游戏，每隔 5 步随机翻转 Agent 的移动指令（比如输入“上”变成“向下移动”），测试 Prompt 如何让 Agent 觉察到规则被篡改并自适应。
  2. **一个中型项目**：**“爱丽丝仙境”规则异化器 (Glitch Craft)**：开发一个 Minecraft 插件，每晚随机修改一种合成表或物理规则（如重力翻转），让 AI Agent 必须自主撰写《异世界生存观察日志》并设法活下去。
  3. **一个艺术/游戏/叙事方向**：**卡夫卡式的动态叙事游戏**：玩家与 AI NPC 共同在一个物理规则每分钟都在“微变”的抽象世界中生存，NPC 会根据规则变动产生心理折磨或宗教式的盲目崇拜。
- 对我项目的启发：设计游戏系统时，不要只给 Agent 静态 API。把“规则改变”本身当作叙事和机制驱动力，能创造极高的系统涌现性（Emergent Gameplay）。
- 今天是否值得深入研究：是
- 建议行动：做demo

## FriendBench: 从非语言交互行为中推断人际“熟络度”
- 来源：arXiv cs.HC
- 链接：https://arxiv.org/abs/2607.29602
- 一句话解释：不听说话的具体内容，仅凭 20 秒的多模态交互行为（肢体、语气、节奏），让 AI 推断两个人是熟人还是初次见面的陌生人。
- 它为什么重要：HCI 和生成式 NPC 的突破点不在于“说了什么”，而在于“怎么说的”（Subtext / 潜台词）。这种对社交“熟络度/潜台词”的量化是创造人情味 AI 的关键。
- 技术趋势标签：#Multimodal #HCI #SocialAI #InteractiveNarrative #SubtextInference
- 可复用模式：**非语言潜台词提取器 (Non-verbal Subtext Extractor)**：过滤显式文本语义，专门抽取肢体、时序、语音语调等隐性信号做社会关系与情绪建模。
- 疯狂发明家灵感：
  1. **一个小实验**：提取两个人对话音频中的“打断频率”和“停顿重叠率”，用简单 Prompt 结合音频特征，判断双方是在“尴尬尬聊”还是“热烈讨论”。
  2. **一个中型项目**：**AI 社交破冰气泡 (Social Ice-breaker Radar)**：一个结合视觉与听觉的桌面小工具，在 Zoom 线上会议时，以粒子视觉实时呈现与对方的“气场同步率”与“社交熟络度”。
  3. **一个艺术/游戏/叙事方向**：**“不能说的秘密”NPC 侦探游戏**：玩家扮演侦探，不需要听 NPC 的对话台词，仅通过观察两个 NPC 站位距离、眼神交汇频率和语气停顿，判断谁和谁私下有不可告人的密谋。
- 对我项目的启发：交互设计中，不要把注意力全放在 Text Prompt 上。“微表情、时间差、交互节奏”才是表达人际关系最硬核的设计素材。
- 今天是否值得深入研究：是
- 建议行动：收藏

## Small Is Enough (InMyStyle): 部署单人专属 LoRA 实现无 Prompt 的个人文风重写
- 来源：arXiv cs.HC
- 链接：https://arxiv.org/abs/2607.29238
- 一句话解释：用本地多个小模型自动构造数据对，微调一个专属的超轻量 LoRA，无需复杂 Prompt 即可将 AI 生成的干瘪文本一键转化为你个人的口吻。
- 消除 AI 废话与 Prompt 冗长终极痛点。用分布式数据构造 + 端侧微型适配器，实现了隐私安全且无感的个人化 HCI 体验。
- 技术趋势标签：#CreativeTools #LoRA #SmallLanguageModels #HCI #PersonalizedAI #Workflow
- 可复用模式：**无感微型权重适配 (Zero-Prompt Personal Adapter)**：将复杂的个人偏好固化在权重的极小层（LoRA）中，把“冗长提示词”降维转化为“底层权重偏好”。
- 疯狂发明家灵感：
  1. **一个小实验**：导出自己微信发过的 100 条短消息，用 Ollama 跑 Qwen-1.5B 训练一个极小的 LoRA，输入标准 AI 废话，看它能否一键吐出带你口头禅的句子。
  2. **一个中型项目**：**设计灵感风格印章 (Personal Design Voice Plugin)**：做个 Obsidian 或 Raycast 插件，读取你过去所有的设计笔记与吐槽，自动为 AI 生成的技术方案注入你独特的“艺术家批判性语调”。
  3. **一个艺术/游戏/叙事方向**：**赛博人格分裂生成器**：为故事中的 5 个不同角色各训练一个 5MB 的微型风格 LoRA，同一段事件剧情经过不同 LoRA 滤镜，瞬间生成 5 个带有极端主观色彩的角色视角日记。
- 对我项目的启发：Prompt Engineering 是暂时的，微型 Adapters/Weights 才是未来个性化创作工具的标准配置。偏好与风格应该被“权重化”。
- 今天是否值得深入研究：是

## Reflection or Re-Generation? 为什么 LLM 的自我修正总是失败
- 来源：arXiv cs.LG
- 链接：https://arxiv.org/abs/2607.28908
- 一句话解释：剖析人类自我修正（细粒度局部修改+假设检验）与 LLM“假反思”（大多只是换个说法重新生成全篇）的根本差异。
- 它为什么重要：现在的 Agent Workflow 疯狂使用 "Self-Reflection" 循环，但很多时候只是在浪费 Token 赌运气。懂了这个研究，就能设计出真正像人类一样的“结构化断点修正”工作流。
- 技术趋势标签：#AgentWorkflow #SpecDriven #SystemDesign #HCI #Metacognition
- 可复用模式：**差分元认知修正 (Diff-based Repair)**：强迫 Agent 产生“修改 Patch (Diff)”而不是重写全文，锁定未出问题的部分，仅对定位错误的片段建立假设并修改。
- 疯狂发明家灵感：
  1. **一个小实验**：设计一个代码修正工作流，强制 LLM 不许输出整段代码，只许输出 `git diff` 格式的修改块，并附带针对该补丁的假设排除说明，观察其一次修复成功率。
  2. **一个中型项目**：**Spec-Driven 代码外科医生 (Spec-Surgeon Agent)**：在 Agent 工作流中引入“假说验证节点”——Agent 修改前必须列出 3 个错误假设，逐一用单元测试排除后，才能生成局部补丁。
  3. **一个艺术/游戏/叙事方向**：**“修改痕迹”交互艺术**：在一个写字板界面上，实时展示 AI 像人类作家一样拿着红笔在文字间画删改线、插入箭头、在旁白打问号的“犹豫与修改过程”，突出创作中“修改”本身的戏剧性。
- 对我项目的启发：不要把 "Reflect and retry" 当作黑盒！Spec-driven development 中，把反思过程强制限定为“差分修改 (Diff) + 规则校验”才是高效 Agent 的本质。
- 今天是否值得深入研究：是
- 建议行动：试用

## 今日模式总结

1. **规则动态漂移 (Dynamic Rule Mutation)**：不要只给 Agent 静态规则系统。允许环境或底层规则发生微小变动，逼迫 Agent 展现“假设-实验-验证”的动态适应能力，这是高涌现性游戏与系统设计的关键。
2. **偏好权重化与无感注入 (Zero-Prompt Adapter)**：将复杂的系统 Spec、文风、个人偏好从 Prompt 中剥离，下沉到轻量级 LoRA 权重中，实现无感、低延时的个性化工具流。
3. **差分修正代替全量重写 (Diff Repair)**：无论是 Agent 代码修补还是文本迭代，抛弃“重新生成”黑盒，采用基于 `diff` 的局部精准外科手术，提升工作流的可控性与可靠性。

## 今日可做小实验

**项目名**：Git-Diff-Surgeon（只许出 Diff 的代码外科医生）

*   **输入**：一段包含逻辑 Bug 的 Python 代码 + 对应的报错信息 (Traceback)。
*   **输出**：标准的 `git diff` 补丁文本 + 1 句话的修改假说说明。
*   **技术栈**：Python + Ollama (或 OpenAI API) + 本地 `patch` 命令行工具。
*   **第一步怎么做**：
    1. 编写系统 Prompt，设置硬性约束：
       > "你是一个代码外科医生。严禁重写全篇代码！你必须先输出一个 JSON: `{\"hypothesis\": \"错误原因说明\"}`，然后输出严格符合 unified diff 格式的 `git diff` 代码块。"
    2. 用 Python 准备一个有小 bug 的 `.py` 文件，把代码和报错喂给模型。
    3. 获取输出后，用 Python 调用 `subprocess.run(["patch", "target.py", "diff.patch"])` 自动打补丁，测试代码是否被成功修复！
