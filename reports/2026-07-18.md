## 1. Code World Models: "能玩"比"预测精准"更重要
- **来源**：arXiv cs.AI (Candidate 13)
- **链接**：https://arxiv.org/abs/2607.14169
- **一句话解释**：研究发现，用 LLM 生成游戏规则代码（代码世界模型 CWM）时，即使代码的单步预测准确率高达 99%，在实际规划和游玩时依然会崩溃；我们必须追求“玩耍充分性”（Play-Adequacy）而非单纯的“预测准确度”。
- **它为什么重要**：对于做游戏生成、Minecraft 模拟或生成式系统的你来说，这是一个巨大的警示：**不要相信 AI 假装生成的完美规则，必须用闭环测试去“玩”它。** 这一理论为“如何评估生成式游戏”提供了硬核的数学和工程支撑。
- **技术趋势标签**：`Code World Models` / `Game Synthesis` / `Play-Adequacy` / `Formal Verification`
- **可复用模式**：**“双轨验证架构”**——一个 LLM 负责疯狂生成/修改游戏规则（代码），另一个经典的搜索/规划算法（如 A* 或 BFS）负责在后台疯狂试玩，只有通关了，规则才算通过。
- **疯狂发明家灵感**：
  1. **一个小实验**：写一个 100 行的 Python 脚本，让 LLM 随机生成一个推箱子（Sokoban）的新规则（比如“箱子可以斜着推”），然后用 A* 算法自动去解。如果解不通，说明规则“不合格”，强制 LLM 重写。
  2. **一个中型项目**：**“规则漂移沙盒”（Rule-Drifting Sandbox）**。一个 2D 平台跳跃游戏，玩家每过一关，LLM 就会修改游戏物理引擎的代码（重力、摩擦力、碰撞逻辑）。后台有一个 AI 玩家在 0.1 秒内模拟试玩，确保这个新物理世界“物理上可通关”后，再呈现给人类玩家。
  3. **一个艺术/游戏/叙事方向**：**《无法终结的西西弗斯》**。一个装置艺术：一个 AI 角色在一个不断随机生成规则的迷宫里行走。迷宫的规则（如“碰到红色会死”或“红色是传送门”）由 LLM 实时生成，但系统确保这个迷宫永远有解，却又极其艰难，AI 角色在其中进行着永无止境的解密表演。
- **对我项目的启发**：在做世界生成或 Agent 规划时，不要只看 LLM 的 Text 输出，把它转化成可执行的 Code（CWM），并用最简单的经典算法去“跑测”它。
- **今天是否值得深入研究**：是（概念极具启发性）
- **建议行动**：做 demo

## 2. MemoHarness: 给 LLM 穿上会自我进化的"外骨骼装甲"
- **来源**：arXiv cs.AI (Candidate 6)
- **链接**：https://arxiv.org/abs/2607.14159
- **一句话解释**：提出了 "Agent Harness"（代理马具/外骨骼）的概念——即包裹在 LLM 外层的控制层（管理上下文、工具、内存、解码）。MemoHarness 能够从每一次的执行失败和成功经验中自我学习，自动优化这个控制层，而不是只靠人去调 Prompt。
- **它为什么重要**：这极度契合你的 spec-driven development 和 agent workflow 兴趣。我们不再是写死一个 Agent 的工作流，而是写一个“会根据经验自己改写自己控制逻辑”的元系统。
- **技术趋势标签**：`Agent Harness` / `Self-Improving Systems` / `Experience Learning` / `LLM Toolchain`
- **可复用模式**：**“反思式包装器”（Reflective Wrapper）**。在 Agent 每次调用工具失败时，不直接报错，而是将失败日志喂给一个“教训提取器”，生成一条“避坑指南”存入 Harness 内存，下次调用同类工具时自动注入。
- **疯狂发明家灵感**：
  1. **一个小实验**：做一个“记仇的翻译 Agent”。每次你纠正它的翻译错误时，Harness 会把你的纠正偏好提炼成一条“规则”（如“主人讨厌‘优化’这个词”），并在后续的所有 Prompt 前置插入这个个性化 Harness 规则。
  2. **一个中型项目**：**“自适应 Spec 编译器”**。你输入模糊的设计 Spec，Agent 生成前端代码。如果代码运行报错，Harness 会记录报错原因，并自动升级自己的“代码生成约束规约”，随着你用的次数越多，它写出的代码报错率越低。
  3. **一个艺术/游戏/叙事方向**：**《性格驯化器》**。一个虚拟宠物，它的 Harness 控制着它的“情绪参数”和“词汇表”。随着玩家对它的态度（温柔或粗暴），Harness 自动修改其解码器的温度（Temperature）和词汇惩罚项（Frequency Penalty），让它从活泼变得抑郁或狂躁，且这种性格改变是代码级、不可逆的。
- **对我项目的启发**：别再手动优化 Prompt 了。把 Agent 运行的 Trace（轨迹）和 Feedback（反馈）变成结构化数据，写一个 Harness 自动把这些数据转化为 Prompt 补丁。
- **今天是否值得深入研究**：是
- **建议行动**：试用 / 收藏其架构图

## 3. Step-Level Preference：让 Agent 的“内心戏”更像人类
- **来源**：arXiv cs.AI (Candidate 1)
- **链接**：https://arxiv.org/abs/2607.14485
- **一句话解释**：传统的社会模拟 Agent 只在任务结束时接受评估，而该研究引入了“步骤级偏好学习”（Step-Level Preference），对 Agent 的规划、记忆检索、反思和行动选择等每一个中间步骤进行微调，让其社会行为极度拟真。
- **它为什么重要**：对于游戏系统、叙事系统和多 Agent 模拟，这解决了“Agent 行为虽然结果对，但动机很假”的问题。通过约束中间步骤（比如：它为什么检索这条记忆？它为什么这样反思？），能创造出有深度、有“灵魂”的 NPC。
- **技术趋势标签**：`Generative Agents` / `Social Simulation` / `Preference Learning` / `HCI`
- **可复用模式**：**“内心戏显微镜”（Internal Monologue Filter）**。在 Agent 做出决定前，强制其生成 3 种不同的“内心反思路线”，并用一个轻量级的“性格过滤器”打分，选出最符合设定性格的那条路线。
- **疯狂发明家灵感**：
  1. **一个小实验**：做一个“多疑的侦探 Agent”。在它回答你的问题前，强制它运行一个“记忆检索反思”：它必须列出 3 条关于你的记忆，并评估“你是不是在骗它”，最后根据这个评估调整它对你说话的语气。
  2. **一个中型项目**：**“戏剧冲突发生器”（Conflict Engine）**。在一个虚拟小镇里放 3 个 Agent，给他们不同的步骤偏好（例如：A 偏好检索悲伤记忆，B 偏好过度解读他人的话）。让他们自由对话，观察他们如何因为“中间认知偏差”而自然产生戏剧性的误会和冲突。
  3. **一个艺术/游戏/叙事方向**：**《读心术剧场》**。一个互动装置，两个 AI 演员在台上对戏，观众手里有红绿按钮。大屏幕上实时投影出演员 A 脑中的“候选想法”（步骤级思考）。观众投票选择 A 应该用哪种“动机”去回应 B，从而实时改变戏剧的走向。
- **对我项目的启发**：在设计 Agent 交互时，把“思考过程”作为一等公民（First-class citizen）暴露给用户或系统，而不是只给一个最终的 JSON 结果。
- **今天是否值得深入研究**：是
- **建议行动**：做 demo

## 4. MCP 协议：打破 AI 与物理模拟器之间的次元壁
- **来源**：arXiv cs.AI (Candidate 5)
- **链接**：https://arxiv.org/abs/2607.14158
- **一句话解释**：探讨了如何利用 Model Context Protocol (MCP) 标准，将多 Agent 系统与复杂的电网数值模拟器进行无缝连接。
- **它为什么重要**：别看它写的是“电网”，把“电网模拟器”替换成 **“Unity 物理引擎”**、**“Blender 场景”** 或 **“TouchDesigner 渲染管线”**，逻辑完全一样！MCP（模型上下文协议）正在成为 AI 读写外部复杂软件状态的黄金标准。
- **技术趋势标签**：`MCP (Model Context Protocol)` / `Multi-Agent` / `Co-Simulation` / `Creative Tools`
- **可复用模式**：**“MCP 创意网关”**。用 Python 写一个通用的 MCP Server，把你的 Creative Coding 工具（如 Processing 或 Max/MSP）的 API 暴露出来，任何支持 MCP 的 LLM（如 Claude）都能瞬间变成这个创意软件的超级外挂。
- **疯狂发明家灵感**：
  1. **一个小实验**：写一个极简的 p5.js MCP Server。让 Claude 能够通过 MCP 协议读取你当前画布上的圆圈位置，并发送指令在旁边绘制一个三角形。
  2. **一个中型项目**：**“LLM 实时灯光控台”**。将舞台灯光控制软件（通过 DMX/ArtNet）包装成 MCP 服务。LLM Agent 作为一个“虚拟灯光师”，通过 MCP 实时监控音乐节奏（输入参数），并动态调整灯光通道数值（输出工具）。
  3. **一个艺术/游戏/叙事方向**：**《生态缸的 AI 园丁》**。一个物理/数字混合生态缸（可以在 Minecraft 里，也可以是实体植物）。传感器数据通过 MCP 传入，AI Agent 作为园丁，通过 MCP 决定何时浇水、调整光照，甚至通过语音向植物“朗诵诗歌”来观察其生长模拟。
- **对我项目的启发**：在构建创意工具链时，不要再自己发明轮子写 Socket 协议了，全面拥抱 MCP，让你的艺术系统原生支持未来的所有前沿 LLM。
- **今天是否值得深入研究**：是
- **建议行动**：试用（强烈推荐去写一个自己的 MCP Server）

## 今日模式总结

1. **Play-Adequacy over Accuracy (玩耍充分性优先)**：评估生成式系统（游戏、代码、世界）时，静态的代码检查和单步预测是骗人的，必须引入一个“自动试玩/运行器”进行动态闭环验证。
2. **The Harness Layer (外骨骼控制层)**：不要把所有逻辑都堆在基座 LLM 或 Prompt 里。在 LLM 外面套一层会自我记录、自我纠偏的 Harness（马具），是让 Agent 稳定且具备个性化记忆的关键。
3. **MCP as the Creative Bridge (MCP 作为创意桥梁)**：MCP 协议不仅仅是给程序员查数据库用的，它是艺术技术（Art-Tech）领域连接 AI 脑腔与物理/视觉执行机构（Blender, TouchDesigner, Arduino）的下一代标准总线。

## 今日可做小实验：2小时极限挑战

### 项目名：Sokoban Drifter (推箱子规则漂移器)
**一句话目标**：做一个“自己进化规则且保证能通关”的文字推箱子游戏。

- **输入**：一个基础的 Sokoban 游戏地图（5x5 字符矩阵）和初始规则（“玩家不能穿墙，只能推箱子”）。
- **输出**：LLM 随机修改游戏规则代码，后台 A* 算法验证可行性，最终输出一个“新奇但绝对能通关”的奇葩关卡。
- **技术栈**：
  - Python 3.10+
  - OpenAI API / Gemini API (用于生成规则 Python 代码)
  - Python `exec()` 函数 (用于动态加载生成的规则类)
- **第一步怎么做**：
  1. 用 Python 写一个极简的 5x5 推箱子游戏类 `Sokoban`，包含 `move(action)` 方法，并写一个简单的 BFS（广度优先搜索）脚本，能在 1 秒内自动解出这个迷宫。
  2. 写一个 Prompt，让 LLM 继承你的 `Sokoban` 类，并重写 `move` 方法（例如：“让箱子在撞墙时反弹”，或者“玩家每走一步，重力方向就会改变”）。
  3. 运行 LLM 生成的代码，立刻用你的 BFS 脚本去跑。如果 BFS 返回 `Unsolvable`（无解）或程序 Crash，就自动报错并把 Traceback 喂回给 LLM 重新生成；如果 `Solvable`（有解），恭喜你，打印出这个新规则和通关路径，开始玩吧！
