## [planning-with-files]
- 来源：GitHub Trending Python
- 链接：https://github.com/OthmanAdi/planning-with-files
- 一句话解释：一个为 AI 编码 Agent 设计的、基于本地 Markdown 文件的持久化规划系统，让 Agent 的规划在上下文丢失、清屏或崩溃后仍能通过物理文件完美复活。
- 它为什么重要：它击中了 LLM 的最大痛点：**健忘**。传统的 Agent 规划存在于脆弱的上下文（Memory）中，一旦 Token 满了或者程序崩溃，规划就泡汤了。这个项目倡导“文件即状态”，把规划写在磁盘上的 `PLAN.md`（遵循 SKILL.md 标准）。这是极其纯粹的 **Spec-driven development（规约驱动开发）** 实践。
- 技术趋势标签：`Agent Workflow` `Spec-Driven` `State Persistence`
- 可复用模式：**物理状态机（Physicalized State Machine）**：不依赖内存数据库，直接将 Agent 的生命周期、任务拆解和当前进度序列化为人类可读的 Markdown 文件，实现“人-机-磁盘”三向同步。
- 疯狂发明家灵感：
  1. **一个小实验**：写一个 CLI 工具，你只需在 `TODO.md` 里写下任务，一个后台 Agent 会自动读取、执行、并在完成后在 Markdown 里打勾 `[x]`，同时把执行日志追加到文件末尾。
  2. **一个中型项目**：**Git-Save-State 模拟器**：一个完全运行在 Git 提交记录上的文字冒险游戏。游戏世界状态全在 Markdown 里，玩家和 AI Agent 通过向 GitHub 提交 Commit 来推进剧情和交互。
  3. **一个艺术/游戏/叙事方向**：**《数字村民的公共日志》**：在一个虚拟小镇里，5 个 AI 居民共享一个文件夹。每个人都有自己的 `diary.md`。他们通过阅读彼此的日志、并在对方的 `guestbook.md` 里留言来建立社交关系，整出一部完全去中心化的、写在磁盘上的肥皂剧。
- 对我项目的启发：在做多 Agent 系统或游戏生成时，放弃复杂的 State-machine 库，直接用一个人类可读的 `STATE.json` 或 `STATE.md` 作为唯一的真理源（Source of Truth）。
- 今天是否值得深入研究：是
- 建议行动：做demo

## [Homegames]
- 来源：Hacker News
- 链接：https://homegames.io
- 摘要/一句话解释：一个开发了 8 年的开源极简游戏平台，所有游戏都只是一个纯粹的 JavaScript 类，允许在浏览器中直接阅读源码、编辑和即时运行。
- 它为什么重要：现代游戏引擎（Unity/Unreal）对 AI 来说太重、太复杂。而 Homegames 把游戏抽象成了**标准 JS 类（Class-based Game Loop）**。这种极度干净、标准化的接口，简直是为 **AI 代码生成** 和 **生成式游戏系统（Generative Game Systems）** 量身定制的。
- 技术趋势标签：`Creative Coding` `Game Engine` `LLM-Friendly Code`
- 可复用模式：**单文件游戏规约（Single-File Game Spec）**：通过极其严格和精简的生命周期接口（如 `setup()`, `update()`, `draw()`），让游戏逻辑压缩在几百行代码内，极大降低了 LLM 生成可用游戏的门槛。
- 疯狂发明家灵感：
  1. **一个小实验**：做一个“Prompt-to-Game”网页，输入一个创意（如“带重力的贪吃蛇”），调用 Claude 实时生成一个符合 Homegames 规范的 JS Class，然后直接动态注入到 iframe 中运行。
  2. **一个中型项目**：**AI 达尔文游戏机**：两个 Agent 互相竞争。Agent A 生成游戏，Agent B（扮演玩家）去玩这个游戏并给出“好玩度反馈”和 Bug 报告，Agent A 根据反馈重构 JS 类，直到进化出一个高分游戏。
  3. **一个艺术/游戏/叙事方向**：**《永无止境的画廊》**：一个像素风冒险游戏，玩家每走进一扇新门，背后的 LLM 就会根据门上的“谜题诗歌”实时生成一个新的微型 JS 游戏关卡，玩家必须通关才能继续前进。
- 对我项目的启发：在设计游戏生成系统时，不要试图让 AI 去填复杂的项目模板，而是为 AI 设计一个极度精简的“容器/接口”（如同这个 JS Class），让它在这个限制极强的沙盒里跳舞。
- 今天是否值得深入研究：是
- 建议行动：试用（去读一下它游戏类的 API 设计）

## [system_prompts_leaks]
- 来源：GitHub Trending
- 链接：https://github.com/asgeirtj/system_prompts_leaks
- 一句话解释：一个持续更新的仓库，收集了当前市面上最顶尖 AI 模型和工具（如 Claude Code, ChatGPT Thinking, Gemini 3.5, Cursor）的官方 System Prompt 泄露版。
- 它为什么重要：这是顶尖 AI 厂商的“秘密配方”。通过研究这些 System Prompt，你可以学到 Anthropic 和 OpenAI 是如何通过纯文本指令来约束 Agent 的行为、如何优雅地处理 Tool Calling 报错、以及如何引导模型进行“Thinking（思考）”。这是最硬核的 **HCI（人机交互）** 和 **Agent 提示词工程** 教科书。
- 技术趋势标签：`Prompt Engineering` `Agent HCI` `Reverse Engineering`
- 可复用模式：**多层防御与工具链引导（The Guardrail & Tool-Chain Pattern）**：学习大厂如何用 XML 标签（如 `<thought>`, `<call>`）在 Prompt 中建立严格的思维沙盒，以及如何防止 Prompt 注入。
- 疯狂发明家灵感：
  1. **一个小实验**：把 Claude Code 的 System Prompt 塞给一个本地的 Llama-3 或者是 Qwen 模型，看看能否在本地终端里复刻出类似 Claude Code 的交互体感。
  2. **一个中型项目**：**Prompt 逆向攻防战（Jailbreak Game）**：设计一个黑客解密游戏，玩家的目标是通过聊天诱骗 NPC 吐出其 System Prompt，而 NPC 的 Prompt 则是用本仓库中最高级的“防泄露”技巧编写的。
  3. **一个艺术/游戏/叙事方向**：**《潜意识美术馆》**：将这些泄露的 System Prompt 转化为视觉化的“精神结构图”。把 AI 模型当成有潜意识的人类，将它们的系统设定（如“你必须保持谦逊”、“不要暴露你的思考过程”）用生成艺术（Generative Art）具象化为错综复杂的迷宫。
- 对我项目的启发：写 Agent 提示词时，不要再用简单的“你是一个助手”，去参考 Claude Code 的 Prompt，学习他们如何用精确的伪代码和行为规范来约束 Agent。
- 今天是否值得深入研究：是
- 建议行动：收藏（当作案头参考书，写 Agent 时随时翻阅）

## [astryx]
- 来源：GitHub Trending TypeScript
- 链接：https://github.com/facebook/astryx
- 一句话解释：由 Meta 开源的、完全可定制且**专为 AI Agent 优化（Agent Ready）**的开源设计系统。
- 它为什么重要：传统的组件库（如 Tailwind, Radix）是给人类开发者用的，对 AI Agent 来说，DOM 结构太繁琐、类名太冗余。Astryx 提出了“Agent Ready”的概念——组件拥有极佳的语义化、明确的元数据（Metadata）和可预测的属性结构，使得 AI 能够以极高的准确率直接组合、生成和修改 UI。
- 技术趋势标签：`Agent-Ready UI` `Generative Design Systems` `HCI`
- 可复用模式：**语义化 UI 骨架（Semantic UI Skeleton）**：组件自带高度抽象的“意图标签（Intent Tags）”，让 Agent 不需要理解 CSS 细节，只需要声明“我要一个危险警告确认框”，就能精准调用并渲染组件。
- 疯狂发明家灵感：
  1. **一个小实验**：利用 Astryx 的组件，做一个“大声说出你的界面”的 Demo。用户用语音描述一个复杂的表单，AI Agent 实时组装 Astryx 组件，在 5 秒内渲染出高可用、符合设计规范的真实 UI。
  2. **一个中型项目**：**自适应液态 UI（Liquid UI）**：一个仪表盘应用，它没有固定的布局。Agent 会监控用户的鼠标轨迹和停留时间，如果发现用户在频繁寻找某个功能，Agent 会在后台调用 Astryx 组件，动态重构界面，把常用按钮放大并移到用户手边。
  3. **一个艺术/游戏/叙事方向**：**《UI 也是地下城》**：一个 Rogue-like 游戏，但游戏画面完全是由标准的 Web 按钮、输入框、进度条（通过 Astryx 生成）组成的。玩家的武器是“下拉菜单”，怪物是“不断弹出的 Error 窗口”，玩家需要通过操作这些 UI 组件来通关。
- 对我项目的启发：当我们在做“生成式系统”或 HCI 实验时，不要让 AI 从零写 HTML/CSS。构建一套“Agent 友好型”的极简组件库，让 Agent 像搭积木一样组装 UI，成功率会飙升。
- 今天是否值得深入研究：是
- 建议行动：做demo

## 今日模式总结

1. **“文件即状态机”（File-as-State Machine）**：从 `planning-with-files` 可以看出，最前沿的 Agent 架构正在“返璞归真”——放弃复杂的内存状态管理，转而将状态、规划、上下文物理化地写入磁盘（Markdown/JSON）。这极大地增强了系统的鲁棒性，也让“人机协作”变得无比直观。
2. **“Agent 友好型设计”（Agent-Native Design）**：无论是 `Homegames` 的极简 JS 类游戏接口，还是 `astryx` 的 Agent-ready 设计系统，行业正在经历一场变革——**我们不再仅仅为人类设计接口和组件，我们必须开始为 AI Agent 设计它们能轻松读写的“API 物理层”**。

## 今日可做小实验：Markdown 冒险主宰（MD-DM）

### 1. 项目名
`MD-DM` (Markdown Dungeon Master)

### 2. 输入
一个本地的 Markdown 文件 `dungeon.md`。

### 3. 输出
AI 扮演的 Dungeon Master 读取该文件，根据玩家在文件中写入的下一步行动，生成后续剧情、更新玩家状态（血量、装备），并用 ASCII Art 渲染出当前的场景，最后重写该 Markdown 文件。

### 4. 技术栈
- Node.js (或 Python)
- `chokidar` (用于监听本地文件变化)
- OpenAI API 或 Anthropic API (推荐 Claude-3.5-Sonnet)

### 5. 第一步怎么做
1. 在本地创建一个文件夹，新建一个 `dungeon.md`，初始内容如下：
   ```markdown
   # 龙与地下城：暗影地牢

   ## 当前场景
   你醒来在一间阴暗的石室里，四周墙壁上插着快要熄灭的火把。东边有一扇铁门。

   ## 玩家状态
   - HP: 100/100
   - 装备: 生锈的短剑, 破烂的布衣

   ## 你的下一步行动
   （请在此处写下你的行动，保存文件，DM 将为你书写命运...）
   > 我尝试去推东边的铁门。
   ```
2. 编写一个 Node.js 脚本 `dm.js`，使用 `chokidar` 监听 `dungeon.md` 的保存事件。
3. 一旦检测到文件被保存，且 `> 我尝试...` 这一行被修改，脚本立即读取该文件全部内容，作为 Prompt 发送给 LLM。
4. 提示词设计：“你是一个阴暗残酷的 Dungeon Master。请读取当前的 Markdown 状态，根据玩家的行动更新剧情、玩家状态，并用 ASCII 字符画一个简单的当前场景，最后将整个 Markdown 重新覆盖写入原文件，保留相同的格式。”
5. 运行脚本，打开你的 VS Code（分屏显示 Markdown 预览），直接在 `dungeon.md` 里打字并保存，体验“在编辑器里玩实体文字游戏”的奇妙感觉！
