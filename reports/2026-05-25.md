## 1. Constraint Decay: LLM Agent 的“约束衰变”现象
- **来源**：Hacker News / arXiv
- **链接**：https://arxiv.org/abs/2605.06445
- **一句话解释**：最新研究发现，LLM Agent 在持续生成代码时，会像放射性元素一样发生“约束衰变”——随着代码量增加，它们会逐渐遗忘或违反最初设定的规则和边界。
- **它为什么重要**：这揭示了 Agent 系统的“熵增”本质。如果你在做 Spec-driven development（声明式驱动开发）或者多 Agent 协作，你不能寄希望于 Agent “一直听话”。你必须设计“约束校验器（Guardrails）”或“物理法则”来对抗这种衰变。
- **技术趋势标签**：#Agent-Workflow #Spec-driven #LLM-Limitations
- **可复用模式**：**“双向拉扯”架构**——一个 Agent 负责疯狂输出，另一个独立的“哨兵 Agent”手持原始 Spec，不做任何开发，只负责挑刺和纠偏。
- **疯狂发明家灵感**：
  1. **一个小实验**：写一个 Git Pre-commit Hook，每次提交代码时，用一个极小的本地模型（如 Llama3）去对比你的 `SPEC.md`，检测当前代码是否发生了“设计漂移”。
  2. **一个中型项目**：**“代码防腐剂（Code Preservative）”**：一个实时运行的 IDE 插件，它将你的架构设计（如“所有 API 必须有超时处理”）可视化为一条条“能量槽”，随着 Agent 编写代码，能量槽会衰减，逼迫你或 Agent 进行“架构重构”来补充能量。
  3. **一个艺术/游戏/叙事方向**：**《衰退世界（Decaying Physics）》**：一个 Minecraft 风格的沙盒世界，世界生成器的规则（如“重力向下”、“水往低处流”）由一个 LLM 实时维持。但随着玩家在世界中存活时间变长，LLM 产生“约束衰变”，世界物理法则开始崩塌（例如重力突然反向，石头变成了液体），玩家必须通过“重写系统 Spec”来修复世界。
- **对我项目的启发**：在做自动化生成系统时，永远不要相信 Agent 的长期记忆。要把“规则验证”写成硬编码的 Linter，或者引入独立的裁判 Agent。
- **今天是否值得深入研究**：是
- **建议行动**：做 demo（尝试写一个基于 Spec 的代码 Linter 脚本）。

## 2. andrej-karpathy-skills (Andrej Karpathy 的 Claude 编程避坑指南)
- **来源**：GitHub Trending
- **链接**：https://github.com/multica-ai/andrej-karpathy-skills
- **一句话解释**：一个高度结构化的 `CLAUDE.md` 文件，提炼自大神 Karpathy 对 LLM 编程缺陷的观察，旨在通过本地规则文件彻底驯服 Claude Code。
- **它为什么重要**：**“项目级 Agent 宣言（Repo-level Agent Manifesto）”**正在成为新标准。无需复杂的微调或 Prompt 工程，只需在项目根目录扔一个 Markdown 文件，就能改变 Agent 进驻该项目时的行为模式和“性格”。
- **技术趋势标签**：#Spec-Driven-Development #HCI #LLM-Toolchain
- **可复用模式**：**“上下文锚定（Context Anchoring）”**——利用特定命名的 Markdown 文件（如 `CLAUDE.md` 或 `SYSTEM.md`）作为 Agent 的“本地物理法则”。
- **疯狂发明家灵感**：
  1. **一个小实验**：在你的 Creative Coding 仓库里放一个 `AESTHETIC.md`，规定：“本仓库只接受 Vaporwave（蒸汽波）风格的 P5.js 调色盘，禁止使用纯黑白。”然后让 Cursor 或 Claude 帮你写前端，看它如何在这套美学框架下挣扎和创作。
  2. **一个中型项目**：**“Agent 物理法则生成器”**：一个 Web UI，允许设计师通过拖拽（例如“保守 vs 激进”、“极简 vs 极繁”）来生成专属于某个代码仓库的 `AGENT_PHYSICS.md` 配置文件。
  3. **一个艺术/游戏/叙事方向**：**《文件夹里的居民》**：一个文字冒险游戏，游戏的关卡就是电脑里的真实文件夹。每个文件夹里都有一个 `RULES.md`（代表该区域的律法）。玩家通过修改这些 Markdown 文件，来改变 NPC Agent 在该文件夹里的行为，从而解开谜题。
- **对我项目的启发**：立刻在自己的所有项目里部署定制化的 `.md` 规范文件，这是提高 AI 辅助编程效率、保持代码美感最廉价且最高效的方法。
- **今天是否值得深入研究**：是
- **建议行动**：试用（直接把这个 `CLAUDE.md` 扔进你常用的代码库里测试效果）。

## 3. plastic-labs / honcho (有状态 Agent 的记忆引擎)
- **来源**：GitHub Trending Python
- **链接**：https://github.com/plastic-labs/honcho
- **一句话解释**：专为构建“有状态（Stateful）”Agent 设计的内存管理库，让 Agent 拥有超越简单 Chat History 的、有深度和关联性的长期记忆。
- **它为什么重要**：目前的 Agent 大多像只有 7 秒记忆的金鱼。Honcho 试图解决 Agent 的“认知连续性”问题。这对于游戏 NPC、长期陪伴型 AI、以及需要多天协作的复杂自动化工作流至关重要。
- **技术趋势标签**：#AI-Agent #Memory-Systems #Game-Systems #Narrative
- **可复用模式**：**“记忆代谢（Metabolic Memory）”**——将信息分类为瞬时感知、工作记忆和长期晶体智力，并设计遗忘机制。
- **疯狂发明家灵感**：
  1. **一个小实验**：用 Honcho 写一个 CLI 日记助手，它不单单记录文字，还能记住你两周前的焦虑点，并在你今天提到类似事情时，主动进行跨越时空的关联分析。
  2. **一个中型项目**：**“无尽叙事空间（Endless Lore Engine）”**：一个跑在后台的 Agent 社区，它们利用 Honcho 的记忆库不断互相交谈、产生误解、形成派系，并自动生成一本不断更新的“世界历史编年史”网页。
  3. **一个艺术/游戏/叙事方向**：**《记忆神殿（The Memory Palace）》**：一个 3D 空间（可以用 Three.js 或 Minecraft 实现），空间里的每一个建筑和雕塑都是由 Agent 的长期记忆实体化而成的。玩家可以通过摧毁或篡改这些 3D 实体，来抹去或修改 Agent 的记忆，从而改变游戏剧情走向。
- **对我项目的启发**：游戏系统和生成式世界最缺的就是“历史感”。通过这种结构化记忆库，可以让生成的游戏世界拥有真正的“时间流逝”和“社会关系演变”。
- **今天是否值得深入研究**：是
- **建议行动**：做 demo。

## 4. Lum1104 / Understand-Anything (代码转交互式知识图谱)
- **来源**：GitHub Trending TypeScript
- **链接**：https://github.com/Lum1104/Understand-Anything
- **一句话解释**：将枯燥的代码库转化为精美、可交互、可提问的知识图谱，践行“能教人的图谱，胜过只能炫耀的图谱”的理念。
- **它为什么重要**：这是极佳的 **HCI（人机交互）+ 创意可视化** 案例。它把高度抽象的逻辑结构（代码）变成了空间化的、可探索的视觉媒介。
- **技术趋势标签**：#HCI #Creative-Coding #Visual-Spatial-UI
- **可复用模式**：**“空间化逻辑（Spatializing Logic）”**——将非视觉的数据关系（如依赖、调用、数据流）映射为人类直觉更易理解的几何空间。
- **疯狂发明家灵感**：
  1. **一个小实验**：把一个复杂的 P5.js 艺术生成代码输入进去，生成它的知识图谱，看看艺术逻辑（如噪声函数、粒子系统）在视觉结构上呈现出怎样的几何对称性。
  2. **一个中型项目**：**“代码生态缸（Code Terrarium）”**：读取你的 GitHub 提交历史，将代码结构生成为一个 3D 的虚拟生态缸。函数是植物，变量是水源，Agent 运行时的每一次函数调用，都是一只发光的萤火虫在植物间飞过。
  3. **一个艺术/游戏/叙事方向**：**《代码地下城（Code Dungeon）》**：一个 Roguelike 游戏，游戏地图的每一层都是由玩家上传的一段真实代码生成的。如果代码里有 Bug，那个位置就会生成一个强大的 Boss；如果代码写得极其优雅，该区域就会变成一个开满鲜花的安全区。
- **对我项目的启发**：AI 时代我们不再缺代码，缺的是“理解代码的维度”。用视觉和空间交互去重新定义“如何阅读系统”，是设计 + CS 跨界学生最容易出彩的领域。
- **今天是否值得深入研究**：是
- **建议行动**：收藏并做 demo。

## 今日可做小实验：2小时极速挑战

### 项目名：美学看守所 (Aesthetic Jailer)
*一个无情的、带有强烈赛博朋克审美偏执的 Git Pre-commit Hook。如果你或你的 AI 助手写出了不符合“赛博朋克美学”的 CSS 代码，提交将被无情拒绝，并伴随着一段刻薄的 AI 审美拷问。*

- **输入**：你刚刚修改的 CSS/HTML 文件。
- **输出**：Git Commit 成功；或者 Commit 失败，并在终端输出一段极其赛博朋克风格的视觉修改建议。
- **技术栈**：Node.js + Husky (Git Hooks 库) + Google Gemini API (或任意免费 LLM API)
- **第一步怎么做**：
  1. 在本地新建一个测试前端项目，初始化 git：`git init`。
  2. 安装 Husky：`npx husky-init && npm install`。
  3. 修改 `.husky/pre-commit`，使其在提交时运行一个本地 Node 脚本 `node check-aesthetic.js`。
  4. 编写 `check-aesthetic.js`：
     - 用 `git diff` 读取即将提交的 CSS 代码。
     - 拼装 Prompt 调用 Gemini API：“你是一个极度偏执的赛博朋克 UI 设计师。检查以下代码。如果它没有使用暗黑背景、霓虹发光（text-shadow/box-shadow）、等宽字体（monospace），请用刻薄的语气拒绝提交，并给出修改意见。如果符合赛博朋克美学，只输出 'APPROVED'。”
     - 如果 LLM 返回的不是 'APPROVED'，则执行 `process.exit(1)` 阻止提交，并将 LLM 的刻薄评价打印在终端。
  5. 故意写一段“白底黑字、使用 Times New Roman”的普通 CSS，尝试 `git commit`，静静欣赏 AI 对你的无情嘲讽。
